# Типизированное размещение данных для общего 64-битного компилятора

Компилятор теперь рассчитывает размещение Word32/ref64 по типам и объявлениям
Limbo, за пределами вручную назначенных кадров исполняемых частных профилей.
Расчёт реализован в `limbo/dis64-layout.c`. Генерации произвольного managed-модуля
Dis64 он пока не добавляет. [English version](dis64-typed-layouts.md).

## Посмотреть настоящий кадр AWM

Соберите host Limbo обычным способом и включите отдельную диагностику:

```sh
LIMBO_DIS64_LAYOUT=1 /host/tools/limbo -I module \
  -o /tmp/awm.dis appl/wm/awm.b 2>/tmp/awm-layout.log
```

Каждая JSON-строка `DIS64_LAYOUT` описывает банк MP или кадр FP функции,
указывая окончательный PC и номер дескриптора обычного Dis. Успешная запись
содержит старый и новый размеры, полную карту map8 и элементы вида
`[старое_смещение, новое_смещение, старый_размер, новый_размер, частный_вид]`.
У текущего `init` AWM первые два элемента такие:

```json
[[32, 64, 4, 8, 12], [36, 72, 4, 8, 10]]
```

Это `ctxt: ref Draw.Context` и `argv: list of string`: отдельные восьмибайтные
корни по смещениям 64 и 72. При этом `int` остаётся четырёхбайтным. Поля
вложенного ADT размещаются рекурсивно с естественным выравниванием. Умножить
старое смещение на два недостаточно. Промежутки выравнивания не получают
читаемых элементов. Текущий `init` AWM вместе с локальными и временными данными
требует 592 байта. Числовой вид — внутренняя диагностика компилятора, не общий
идентификатор типа Dis64.

Полученный выше `.dis` остаётся обычным старым Dis. Переменная окружения не
меняет инструкции, дескрипторы, хэши, инициализацию или выбранную цель.
С `-64l` получаются такие же планы, после которых действующий backend всё ещё
отклоняет общий managed-код AWM. Исполняемый образ AWM не создаётся.

## Типы и роли адресов

Поддержаны byte/int/fix/big/real, String, ref, array, list, channel, module и
размещение полиморфной ссылки; вложенные tuple/ADT/exception; аргументы,
глобальные и локальные данные, совместимые переиспользуемые локальные слоты.
Расчёт останавливается на ссылке: переменная массива — корень, а не встроенное
содержимое массива. Тип элемента можно отдельно передать в `dis64layouttype`.
Рекурсивные ссылки поэтому конечны, а цикл по значениям отклоняется.

Для каждого конкретного варианта pick ADT рассчитываются тег, общие поля и
его собственные поля. Неспециализированный базовый pick отклоняется: объединять
карты всех вариантов нельзя, иначе GC может принять скаляр другого варианта
за указатель. Установка heap-дескрипторов, выделение pick и переход по тегу
в loader этим шагом ещё не реализованы.

В таблицах компилятора роли различаются явно:

| Данные | Размер на 64 битах | Корень GC |
| --- | --- | --- |
| Прямая ссылка `alt` на channel/array | 8 | Да |
| Адрес ячейки channel или данных `alt` | 8 | Нет |
| PC перехода в числовом/строковом case | 4 | Нет |
| Строковая граница case | 8 | Да |
| Кодированная таблица имён импорта | Сохранённые байты | Нет |

Заимствованные адреса, координаты кода и непрозрачные записи импорта нельзя
прочитать через обычное разрешение скалярного адреса или ссылки. Перезапись
целей case и генерация записей импорта ещё требуют отдельных путей. Расчёт
их размещения сам по себе не делает таблицы исполняемыми в новом ABI.

## Интерфейс компилятора и отказы

`dis64layouttype` рассчитывает тип. `dis64layoutstorage` объединяет настоящие
объявления аргументов, локальных или глобальных данных и сверяет каждый корень
со старым дескриптором. `dis64layoutaddress` разрешает одно полное типизированное
чтение либо часть скаляра. Роль: 0 — скаляр, 1 — managed-ссылка, -1 —
заимствованный нативный адрес. Padding, часть указателя, чтение через границу
поля и неправильная роль отклоняются. Заголовок кадра, адрес результата и
зарезервированные временные ячейки VM остаются задачей соглашения о вызовах.

План владеет своими элементами, но только заимствует AST. Перед вызовом его
нужно обнулить, после успеха или отказа вызвать `dis64layoutfree`. Частичный
план с причиной отказа не разрешает адресов. Исходные типы, смещения, карты и
сигнатуры не переписываются. Ограничены размер объекта (1 MiB), число элементов
(65536), глубина (128) и работа сравнения общих локальных слотов. Перекрытия,
несогласованные алиасы, неверные размеры скаляров и необъяснённые корни
дескриптора отклоняются.

## Проверка

```sh
python3 utils/tests/dis64-layout.py --limbo /host/tools/limbo
```

Тест независимо читает дескрипторы полученного обычного Dis и проверяет 376
банков всех 16 модулей стартовой цепочки AWM. Старый байткод сравнивается
побайтно; `-64l` обязан сохранить отказ и те же планы. Ключ
`--baseline /previous/limbo` дополнительно сравнивает с предыдущим компилятором.

C-тест сверяет `sizeof`, выравнивание и `offsetof`, вложенные поля, алиасы,
варианты pick, роли alt и таблицы case; проверяет испорченные метаданные и
полное освобождение выделений. Три намеренно убранных условия обязаны нарушить
соответствующие семантические проверки. Для кросс-запуска есть `--c-only`,
`CC`, `NATIVE64_CFLAGS`, `NATIVE64_RUNNER`. Пройдены AMD64 ASan/UBSan и
ARM64 UBSan/QEMU. LeakSanitizer недоступен в текущей ptrace-среде; баланс
выделений теста проверяется явно при выключенном сканировании утечек ASan.

Следующая интеграция — применение смещений с учётом opcode, связывание
результатов caller/callee, дескрипторы содержимого, генерация инициализаторов
и таблиц, общий допуск managed-модулей загрузчиком. Исключения и variadic-хвосты
также остаются работой. Этот этап не запускает AWM и не даёт готового GUI APK.

Первый потребитель теперь использует эти планы для адресов аргументов FP/MP,
вложенных инициализаторов и проверенной проекции прямых копий структур.
[Типизированные переносы](dis64-typed-source-lowering.ru.md) описывают выполнение
обработчиками VM и оставшуюся интеграцию общих managed-образов.
