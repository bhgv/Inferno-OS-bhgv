# Запросы из `.m` и чтение библиотек через namespace

[English version](dis64-scalar-namespace.md).

Скалярный библиотечный путь теперь соединяет запросы интерфейса, сгенерированные
Limbo из `.m`, с чтением namespace, штатным допуском файла и proof всего provider.
Внешний импортирующий клиент в этой проверке — нативный C. Допуск гостевой команды
LOAD и сериализованный managed-клиент остаются следующим участком.

## Интерфейс клиента

Для [примера Library](dis64-scalar-libraries.ru.md):

```sh
limbo -64b -I . -o library.dis64 library.b
limbo -H -R -M Library library.m > library-native64.h
```

Необязательный `-R` требует `-H -M <модуль>`. Обычный вывод `-H` не меняется.
Дополнительно выдаются:

- `limbo_native64_Library_scalar_imports` — полный payload существующей Imports;
- `limbo_native64_Library_scalar_strings` — полный payload существующей Strings;
- `LIMBO_NATIVE64_IMPORT_Library_mid` и аналоги — ordinal-запросы.

Это байты интерфейса и индексы. Здесь нет PC provider, карт его кадров или
указателей на нативные функции. Запрашиваются все функции `.m`, включая
неиспользованные. Runtime сопоставляет таблицу целиком: отсутствующий лишний
экспорт отклоняет загрузку. Порядок links соответствует этой таблице и не зависит
от порядка экспортов provider.

Signaturev1 сохраняет void/int/big/real и порядок аргументов. Big и Real остаются
разными при одинаковой ширине. Пределы:64 функции,64 аргумента на функцию,
255 ASCII-байт имени модуля/функции. Представим и пустой интерфейс. Managed,
byte/fixed, агрегаты по значению и variadic остаются вне этого scalar-producer.
Без `-R` генератор `-H` сохраняет прежнюю более широкую поддержку типов.
Неподдержанная семантика scalar-request отклоняется до C-вывода. Защита
зарезервированных C-префиксов сохраняется.

Прежние хэши `.m`, C-кадры и проверки раскладки остаются в заголовке. 32-битные
хэши не придумываются и не заменяют структурную файловую сигнатуру. Заголовок —
метаданные клиента, а не реализация provider. Два массива payload не являются
самостоятельным модульным файлом. Новых публичных wire-ID нет.

## Чтение и создание экземпляра

```c
Modlink *read64calllibrary(
    char *path, int jit,
    const uchar *imports, ulong importbytes,
    const uchar *strings, ulong stringbytes,
    int sync);
```

До первого обращения к namespace выбирается существующий стартовый режим
`dis64-calls`. Reader фиксирует/проверяет его; имя или содержимое файла режим не
выбирают. Default и выключенная сборка отказывают до namespace/конструктора.
Нужны DIS64_PILOT_LOADER=1 и совместимый WORD32/ref64. Путь непустой, до1023 байт,
с обычным namespace lookup. `$...` сохраняет отдельный путь встроенных модулей.

После включения сгенерированного заголовка, в требуемом VM-контексте:

```c
ml = read64calllibrary("/lib/library.dis64", 1,
    limbo_native64_Library_scalar_imports,
    sizeof(limbo_native64_Library_scalar_imports),
    limbo_native64_Library_scalar_strings,
    sizeof(limbo_native64_Library_scalar_strings), 1);
if(ml == nil)
    return 0;
/* Перенести ml в размеченный VM-root по обычным правилам ссылок/barrier. */
/* Затем снять один временный root: ptrdel(D2H(ml)). */
```

Для штатного MFRAME/MCALL используется `LIMBO_NATIVE64_IMPORT_Library_mid`.
Соответствующий link содержит доказанный VM-PC и настоящий Type кадра provider.
Это не указатель для прямого C-вызова. Frame64/RET/JIT сохраняют свои правила.
Создание экземпляра не вызывает функций, включая `init`.

Нативные буферы пути/запросов/строк остаются доступными и неизменяемыми на всё
время вызова, в том числе при отпускании VM. Sync=1 требует контекст, которому
разрешён release: обычные release/isave и acquire/irestore окружают только
защищённое файловое чтение. Прежний запрет release при активном синхронном
caller-lease сохраняется. Sync=0 держит exclusion на всём I/O. На возврате
exclusion удерживается.

Reader владеет Dir, буфером образа и FD, соединяет короткие чтения, проверяет
каждый счётчик относительно остатка. Положительная длина ограничена прежним
пределом образа до выделения буфера. FD закрывается перед допуском; нативный
kclose потребляет принадлежащий ему дескриптор при любом возвращённом статусе.
Ошибки I/O и защищённых callbacks освобождают временные ресурсы.

После acquire штатный mustbesigned вызывается до proof-workspace библиотеки и
VM-владельцев. Затем конструктор сопоставляет полные запросы и доказывает все
функции перед созданием Types/code/JIT и закреплённого экземпляра. Dontcompile
проверяется после I/O, включая изменение политики при отпущенной VM. После
успешного возврата входные буферы можно уничтожить.

Успех возвращает одну ссылку Modlink и один внешний GC-pin. Отказ — nil без
частичного экземпляра или pin. Для отказа от ещё не опубликованного результата
под exclusion: ptrdel(D2H(ml)), затем destroy(ml). Остальные правила владения
даны в [контракте библиотек](dis64-scalar-libraries.ru.md).

## Допуск каждого файла

Каждый вызов заново открывает, читает, допускает, доказывает файл и создаёт новый
незарегистрированный экземпляр. Module cache и legacy hash lookup здесь не
используются; старый одноимённый модуль не подменяет допуск. Возможность повторного
использования файловой идентичности через кэш не выдаётся. Обычная семантика
изменения файлов и прав остаётся за существующими namespace/admission.

Обработчик гостевого ILOAD не изменён. API закрывает файловую половину для
будущего допущенного caller. Managed-граф, встроенные импорты и смешение
legacy/native ABI этим шагом не открываются. Layout Module/Frame, публичные
Dis64/ISA-ID, версия сигнатуры и vendor pin не меняются.

## Воспроизведение

```sh
python3 utils/tests/dis64-scalar-requests.py --limbo /host/limbo
python3 utils/tests/dis64-library-namespace.py --limbo /host/limbo
for control in admission close acquire profile; do
    python3 utils/tests/dis64-library-namespace.py --limbo /host/limbo --control "$control"
done
python3 utils/tests/dis64-library-namespace.py --limbo /host/limbo --disabled
```

Для ARM64/Linux QEMU используются CC/NATIVE64_ARCH/NATIVE64_RUNNER/NATIVE64_CFLAGS.
Для host ASan/UBSan задайте sanitizer-флаги и `--materialize-only`: проверяются
чтение, допуск, построение и отказы без VM-инструкций. Прежнее ограничение
runtime-ASan при unwind остаётся открытым.

14 настоящих интерфейсов/provider проходят по672 scheduler-root на x64 и ARM64:
четыре сочетания C/RX client/provider, помещающийся/расширяющийся стек, кванты
1/3/1000 и оба I/O-режима. Проверяются биты ответа, успешный RX нормальных
запусков, уничтожение входных буферов, отсутствие автоматической init и явные
ошибки. Ошибочный код может использовать C fallback. Независимые изменения `.m`
добавляют несуществующий экспорт или меняют Big на Real; загрузка отклоняется до
исполнения. Обычный `-H` совпадает с прежним компилятором для14 интерфейсов и пяти
предельных примеров. Проверены пять producer-границ,12 корректно типизированных
неподдержанных интерфейсов, два зарезервированных имени и три ошибки CLI.

Оба runtime-gate проверяют каждое выделение чтения/конструктора, финальный pin,
запрет/исключение допуска, девять I/O-отказов, полные/неверные длины, повреждённые
файлы/запросы, `$`-пути, кэш-алиас и политику JIT. Четыре отключения требуют
точного semantic-exit10 с очисткой fixture при потере допуска, FD-cleanup,
acquire или стартовой политики. Только тестовая граница восстанавливает
пропущенный acquire перед диагностикой; неверные модули не исполняются.

Тела reader/планировщика штатные. Транспорт namespace, предикат допуска, GC/pin
и OS-стыки ограничены fixture. Это не новый положительный полный OS guest-LOAD
или доказательство конкурентной файловой/GC-семантики. Полные консоли отдельно
пересобраны и проверены регрессией. Android/Bionic GUI, AWM и рабочий APK пока не
подтверждены. [Отчёт INFERNO-0180](dis64-inferno-namespace-report.md).

[Продолжение: структурный ILOAD](dis64-scalar-iload.ru.md) связывает собственные
таблицы вызывающего модуля с инструкцией VM. Допуск клиентского файла остаётся
отдельным следующим шагом.
