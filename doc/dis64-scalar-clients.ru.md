# Limbo-клиент из файла загружает скалярную библиотеку

Здесь описана база0182. Текущий компилятор также поддерживает
[ветки, циклы и nil-проверки module](dis64-client-control-flow.ru.md).

[English version](dis64-scalar-clients.md).

Теперь ограниченная Limbo-команда компилируется в dis64 и запускается полным
эмулятором Inferno. Код клиента и библиотеки читается из файлов. Клиент сам
исполняет ILOAD, проверку файла и интерфейса, MFRAME/MCALL. C-описание инструкций,
карт корней и импортов клиента больше не требуется. Android GUI/AWM пока остаётся
следующей отдельной задачей.

## Интерфейс и два исходника

`library.m`:

```limbo
Library: module {
    PATH: con "/demo/library.dis64";
    inc: fn(n: int): int;
};
```

`library.b`:

```limbo
implement Library;
include "library.m";
inc(n: int): int { return n+1; }
```

`client.b`:

```limbo
implement Client;
include "library.m";
Client: module { init: fn(); };
init() {
    m := load Library Library->PATH;
    first := m->inc(7);
    m = load Library Library->PATH;
    last := m->inc(first);
}
```

Скомпилируйте новым host-компилятором, поместите файлы в `/demo` корня эмулятора:

```sh
limbo -64b -I . -o library.dis64 library.b
limbo -64c -I . -o client.dis64 client.b
emu -r /path/to/inferno-root -X dis64-calls -c 1 -d /demo/client.dis64
```

`-c 0` выбирает C-интерпретацию. Пример получает8, затем9 и ничего не печатает:
импорт Sys в этот поднабор не входит. `Library` описывает интерфейс,
`Library->PATH` задаёт имя файла, а `load` компилируется в инструкцию Dis.
Никакой автоматический init библиотеки при загрузке не вызывается. Экспорт init
остаётся обычной функцией, которую можно вызвать явно.

Для файлового клиента C-заголовок `-H -R` не нужен. Запросы берутся из финальной
LDT компилятора и объявлений функций `.m`. Порядок импортов сохраняется; записываются
все записи выбранной LDT. Неиспользуемые объявления, исключённые обычным сужением
Limbo-интерфейса, обратно не добавляются. Это отличается от opt-in заголовка для
C-встраивания, который запрашивает весь `.m`. Контракты обоих путей сохраняются.
Каждый записанный запрос проверяется целиком;32-битный хэш не подменяет signaturev1.

## Допускаемый клиент

Один init без аргументов и результата, один постоянный ASCII-путь. Один module
local можно загружать повторно. Параметры и результаты вызовов — void/int/big/real;
аргументы заранее вычислены в скалярных локальных переменных либо Word-immediate.
Результат можно передать следующему вызову или использовать в вычислениях.
Библиотеки сохраняют прежнюю поддержку скалярных DAG-вызовов и ветвлений в листьях.

Клиент пока линейный: Word/Big-перемещения, целочисленная арифметика и битовые
операции, сдвиги, преобразования Int→Big/Real, Real-перемещения. Ветки, циклы,
дополнительные функции, module globals, ссылочные параметры/результаты, операции
кучи, обработчики исключений и динамические/разные пути отклоняются.
Подготовка аргументов должна состоять из перемещений. Если компилятор сливает
арифметику прямо с записью аргумента в готовящийся кадр, такая форма пока не входит
в producer; вычислите local, который используется и после вызова.

Пределы producer:128 исходных IR-инструкций и4096 байт итогового кадра. Raw-проверка
дополнительно ограничивает256 инструкций,64 импорта/аргумента и64 скалярных span.
Имена — непустой ASCII до255 байт, путь —1–1023 ASCII-байта без `$...`.
Большие числовые константы, требующие дополнительного MP, пока отклоняются;
используйте локальные значения и поддержанные преобразования.

Если библиотека отсутствует или несовместима, load возвращает nil/H, а следующий
вызов даёт штатное `module not loaded`. Ветки проверки nil и обработчики ещё не
допускаются. `$Sys` и `$self` сохраняют отдельные прежние пути; общего допуска
native builtins здесь нет.

## Проверка файла и владение

Используются существующие пять секций Module/Code/Types/Imports/Strings и
signaturev1. Частная форма допуска Inferno фиксирует скалярный entry frame без
корней,24-байтовый mapped MP и одну таблицу импорта. В String pool:0 — имя команды,
1 — путь,2 — интерфейс,3+ordinal — имя функции. Конструктор создаёт собственную
String пути: MP0/8 изначально H, MP16 содержит эту String. Это ограниченное
соглашение запуска Inferno, а не новый общий managed DATA initializer или
заявление о запуске того же файла FlashVM.

Raw-проверка без выделений разбирает весь файл и доказывает роли корней, loads,
группы подготовки/вызова, выравнивание и типы аргументов, ordinal, хвостовую ячейку
результата, его копирование и определённость скалярных значений. Span не могут
пересекаться или менять вид. Нет скрытых веток и доступа к native-заголовку Frame64.
Каждый подготовленный кадр доходит до своего вызова; ошибка библиотеки использует
штатную раскрутку. При отказе выходной view не меняется. Компилятор выполняет эту
же независимую raw-проверку до единственного Bwrite payload.

После доказательства runtime создаёт Types, код, MP, String и копии запросов.
MP удерживается внешним pin на протяжении конструктора/JIT. Защищённые отказы
снимают только приобретённый pin и освобождают все частичные объекты. При успехе
временных pin нет: вызывающий должен зарегистрировать/опубликовать Module до
следующей собирающей VM-операции, как сразу делает parsemod под exclusion.
Конструктор не заменяет проверку файла: политика подписи остаётся в parsemod.
Экземпляры используют штатное клонирование MP; библиотеки по-прежнему читаются и
проверяются заново без кэша.

Доверенный callback чтения устанавливает только проверенный конструктор. Для
файлового клиента запрос JIT берётся из host cflag при LOAD; dontcompile повторно
проверяется после I/O. C-встраивание сохраняет свой явный JIT-параметр.
Внутренний bit29 отличает этот конструктор и не читается из wire-флагов.
Публичные ID/ISA/signature, Frame64/Module/Modlink layout и vendor pin не менялись.

## Воспроизведение

```sh
python3 utils/tests/dis64-scalar-client-producer.py --limbo /host/limbo
python3 utils/tests/dis64-scalar-client-proof.py --limbo /host/limbo
python3 utils/tests/dis64-scalar-client.py --limbo /host/limbo
python3 utils/tests/dis64-scalar-client-boot.py \
    --limbo /host/limbo --emu /root/emu/Linux/o.emu-g --root /root
```

Для ARM64/Linux QEMU используются CC/NATIVE64_ARCH/NATIVE64_RUNNER. Контроли raw
проверки отключают initialized/result/map predicate; повреждённый код не исполняется.
ASan/UBSan конструктора запускается с `--materialize-only` и sanitizer-флагами
NATIVE64_CFLAGS. Прежнее ограничение runtime-ASan при раскрутке ошибок остаётся.

17 пар исходников дают1632 запусков на платформу: C/RX клиента/библиотеки, рост
стека, кванты1/3/1000, отказы открытия/доступа и отключение JIT. Проверяются точные
биты результата и настоящие принятые RX-входы, отравление файла клиента до startup
и каждая ошибка выделения чтения/конструктора. Namespace/GC в этой матрице ограничены
тестовой поддержкой.

Отдельно полные консоли запускают по34 C/RX файловых клиента с настоящими namespace,
кучей, клонированием MP и планировщиком. Корректно типизированная, но неверно считающая
библиотека срабатывает на проверке результата внутри команды. Несовместимая сигнатура
и отсутствующий файл дают `module not loaded` и штатное освобождение процесса.
Обычный профиль и испорченная карта корней отклоняются до исполнения.
Это уже положительный full-OS запуск импортирующего файла. Конкурентный GC/FS stress,
общие managed-графы и готовый Android GUI APK этим не доказаны.
