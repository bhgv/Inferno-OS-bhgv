# Вызовы-посредники из исходников Limbo

[English version](dis64-typed-forwarding.md).

В предыдущем наборе [реальных стековых вызовов](dis64-typed-calls.ru.md)
посредник задавался на C. Теперь целая функция вида `return helper(args)`
переносится из проверенного IR Limbo: FRAME, все аргументы в порядке объявления,
унаследованный адрес результата, CALL в точное начало функции и RET.
Следующая функция тоже может быть таким посредником. Циклы и глубина свыше64
активных функций отклоняются. Кадры сохраняются: это обычный CALL/RET.

```limbo
implement Forward;
Forward: module {
    count: fn(n:int):int;
    relay: fn(n:int):int;
    chain: fn(n:int):int;
};
count(n:int):int {
    total:=0;
    while(n>0){total+=n;n--;}
    return total;
}
relay(n:int):int { return count(n); }
chain(n:int):int { return relay(n); }
```

Проверки запускаются из корня репозитория с хостовым Limbo этой ветки:

```sh
python3 utils/tests/native64-typed-tail.py --limbo /path/to/host/limbo
python3 utils/tests/dis64-typed-tail-unit.py
```

Для ARM64/Linux задайте `CC=aarch64-linux-gnu-gcc`, `NATIVE64_ARCH=arm64`
и `NATIVE64_RUNNER='qemu-aarch64 -L /usr/aarch64-linux-gnu'`.
Проверка IR использует тот же CC/runner без необходимости NATIVE64_ARCH.
Оба набора добавлены в native64-port.py.

Получение частного отчёта компилятора:

```sh
LIMBO_DIS64_TYPED=1 LIMBO_DIS64_TYPED_TAIL=1 \
    /path/to/host/limbo -i -o Forward.dis Forward.b
```

Существующий ключ `-i` отключает встраивание исходных функций и оставляет
вызовы видимыми. Выходной Forward.dis остаётся классическим байткодом;
эта команда ещё не создаёт загружаемый64-битный модуль.

Проверяется точная целевая функция и её дескриптор кадра. Каждая запись
аргумента сопоставляется с объявлением, старым смещением, командой и новой
раскладкой. Поддержаны byte/int/fix/big/real и управляемые ссылки, включая
смесь разных размеров. Aggregate-копии и varargs пока отклоняются.
Все потомки должны успешно переноситься; полную совместимость типов
обеспечивает исходный typechecked IR, а не чужие метаданные.

Унаследованный адрес результата в старом коде читается через FP[16]+0.
В новом коде MOVL переносит все8 байт из FP[32] в поле32 подготовленного
кадра. Обычный Word32 LEA не выполняется. Подготовленный указатель хранится
в немаркированном служебном поле40; владелец результата остаётся живым
в штатной цепочке стека. Нового opcode или изменения Sys gateway здесь нет.

Принятый посредник использует частную схему inferno-typed-tail-v1 с полем
tail=[старый_PC_callee,старый_ID_дескриптора]. Листья сохраняют v2.
Инструкции шестипольные; значение64 в последнем поле обозначает запись
через подготовленный указатель40. Это отдельный контракт: старый адаптер
листовых тел его отклоняет. native64typedtailcode получает от доверенного
сборщика модуля согласованные Type/entry/ordinal; проверяет представимость
и структуру до изменения выхода, без аллокаций и callbacks. Полная смысловая
проверка метаданных и владение входами остаются обязанностью компилятора
и сборщика. Входной и выходной массивы должны быть раздельны.

На x64 и ARM64/QEMU прошли по288 запусков18 исходных функций:6 листьев,
12 посредников, C/RX, цепочки, рост стека, разные кванты и значения.
Проверены соседние байты скаляров и точное освобождение ссылок.
String/list identity здесь передают непрозрачные владеющие графы;
операции над настоящими строками/списками/Unicode/GC проверяет прежний набор.
Конкурентный GC и планировщик ОС этот ограниченный тест не моделирует.

Дополнительно проверены5 аргументов разных размеров,5 отказов в исходниках,
3 проверки с удалением условий компилятора,2 условия нативного адаптера
и8 отказов без частичной записи выхода. Смысловой отказ обязателен;
crash, timeout и sanitizer failure успехом не считаются.

Обычный анализ AWM остаётся14/346. При одинаковом `-i` сравнение с предыдущим
компилятором даёт17 из380 и до, и после: новых принятых тел AWM не заявляем.
Прежний байткод16 исходников,376 планов и191 частного образа сохранён.

На C пока остаются внешний тестовый вход и начальная привязка результата;
все промежуточные вызовы этой цепочки уже получены из Limbo.
Общий вызов с локальным результатом, вычисления после CALL, ветвления,
void/MCALL, writer/loader управляемого модуля и старт Android GUI ещё впереди.
Это проверка ARM64/Linux QEMU, не Android/Bionic, AWM или готовый APK.

Local-result calls and continuations: [dis64-typed-local-results.ru.md](dis64-typed-local-results.ru.md).
