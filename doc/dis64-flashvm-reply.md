## 1. Базовый ABI и механизм расширений

Согласен разделить четыре независимых проверки:

1. Версия wire format: как читать файл.
2. ABI: размеры/выравнивание, карты, кадры, вызовы и представление значений.
3. Обязательные возможности VM: новые инструкции, типы или семантика исполнения.
4. Импорты: конкретные модули, их структурированные интерфейсы и доступность.

Предлагаю для первой версии **список обязательных расширений с именами**, а не
фиксированную глобальную битовую маску. Небольшую маску можно исчерпать, а
независимое распределение её битов создаёт коллизии между двумя репозиториями.

Запись расширения, поля big-endian, без неявного padding:

| Поле | Кодирование |
| --- | --- |
| name_bytes | u16, 1..255 |
| major | u16 |
| minimum_minor | u16 |
| reserved | u16, обязательно 0 |
| name | name_bytes ASCII-байтов, без NUL |

Имена — канонические namespace-qualified строки из `[a-z0-9._-]`, начинающиеся
с буквы; например, префиксы `inferno.` и `flashvm.`. Это примеры пространств,
не регистрация конкретных возможностей. В файле записи отсортированы по имени;
дубликаты запрещены. Реестр имён и их семантики общий, в Inferno/doc с зеркалом
в FlashVM; имя уже опубликованной возможности нельзя переопределить.

Исполнитель поддерживает major точно и minor не ниже требуемого **только когда
реестр обещает обратную совместимость minor**. Ломающая семантика требует нового
major; независимая возможность — отдельного имени. Неизвестное обязательное
расширение, неизвестный major или недостающий minor дают отказ до исполнения.
Не угадывать смысл неизвестного opcode по его числовому диапазону.

В v1 все записи этого списка обязательны. Необязательные debug/provenance
метаданные размещать в необязательных секциях, а не смешивать их с требованиями
исполнения. Разрешённость пропуска секции не позволяет пропускать неизвестную
семантику исполняемого кода.

Новые opcode IDs распределять в общем реестре с привязкой к расширению. В первой
версии не вводить произвольное переименование opcode по номеру списка в файле.
Числа выделяются совместно до появления emitter/loader, а не задним числом.

Важно: UI по типизированным каналам, внешний C-модуль или обычный сервис IDE
не обязаны быть расширением VM. Если достаточно существующих типов/команд,
это **импорт библиотеки**, а не новый ABI и не новая capability instruction set.
Общий базовый Dis64 выполняется в обеих VM при наличии объявленных импортов.

## 2. Header/discriminator: конкретный кандидат

Предлагаю новый распознаваемый prefix/magic и явный фиксированный header.
Не использовать старые classic/NC64 magic. Значение нового magic и abi_id
заполняем из общего реестра после согласования; пока это не числа для кода.

Кандидат: первые 32 байта, все числовые поля big-endian:

| Offset | Поле | Размер |
| ---: | --- | ---: |
| 0 | Новый magic/prefix, точные 8 байтов ещё согласовать | 8 |
| 8 | format_major, кандидат 1 | u16 |
| 10 | format_minor, кандидат 0 | u16 |
| 12 | header_bytes, включая manifest расширений и section directory | u32 |
| 16 | abi_id общего layout/calling contract | u32 |
| 20 | flags, для первой версии 0 | u32 |
| 24 | required_extension_count | u32 |
| 28 | section_count | u32 |

После фиксированной части идут записи расширений из раздела 1, затем directory.
Запись directory: `section_kind:u16, section_flags:u16, offset:u32, length:u32`.
Секции идут по возрастающему offset, не пересекаются, находятся после header
и целиком внутри файла. Header имеет ровно объявленную длину: скрытого padding
или произвольных байтов между manifest и directory в первой версии нет.

Предлагаемая семантика section_flags: бит 0 означает required; остальные биты
в v1 нулевые. Неизвестная required-секция отвергается; неизвестная optional
пропускается только после проверки её границ. Это предлагаемое кодирование,
не занятые сегодня section IDs. Обязательные виды для module/code/type/data/
imports/exports и отдельный control-table kind нужно перечислить в общей spec.
Повторы singleton-секций отвергаются. Нулевые длины определять по kind явно.

Файловые offset/length в этом кандидате ограничены u32; это не означает,
что code operands тоже получили 32-битное кодирование без ограничений.
Для существующего signed30 сохраняется `-2^29 .. 2^29-1`. Layout bounds,
wire bounds и allocation bounds проверяются отдельно. Суммы/произведения при
разборе проверяются на переполнение до allocation и чтения диапазона.
Реальные лимиты памяти/числа секций исполнитель задаёт явно; u32 не означает
разрешение выделить любое число записей по входному count.

Предлагаю сохранить canonical big-endian scalar payloads, где они уже определены
в Dis. Int занимает ровно 4 байта, big и binary64 — 8; C padding и native pointers
не сериализуются. Nil имеет отдельную wire-инициализацию ссылки, которую loader
переводит в runtime nil; это не молчаливая смена существующего `H` на C NULL.

Неверные major/ABI/flags/extensions должны отвергаться до ABI-зависимого
размещения heap/stack и релокаций. Проверка имён/границ manifest использует
ограниченные временные данные, а не выделение объектов исполняемой программы.
В подписанном варианте header/ABI/manifest должны входить в проверяемое
содержимое; конкретная схема подписей здесь не разрабатывается.

Готов принять более компактный header, если Inferno предложит конкретные
байты с теми же четырьмя независимыми проверками. Прошу ответить по этому
кандидату целиком, а не отдельно назначать несовместимые номера в каждом repo.

## 3. FIR entry/result/call: не заводить второй публичный ABI

Предлагаю **один обычный Dis calling ABI для всех публичных вызовов**, независимо
от происхождения функции: Limbo → Dis, Limbo/AS → FIR → Dis или native module.
Собственная FIR SSA-модель и нынешний test capture не должны становиться вторым
публичным calling ABI.

Поддерживаю кандидат Frame64: runtime `lr/fp/mr/t` по offsets 0/8/16/24,
result pointer 32, STemp/RTemp/DTemp 40/48/56, следующие данные от 64.
Аргументы/локальные значения размещаются по declared type и alignment,
а не универсальными восьмибайтовыми ячейками для любого int.
Это описание VM frame, **не SysV/Windows/AAPCS native C ABI**.

Result pointer указывает на подготовленный caller-ом слот declared return type.
Callee записывает значение соответствующей ширины; правила передачи ref-results
должны явно определять retain/release и принадлежность слота. Для void слот
не разыменовывается. Для первого scalar target достаточно int/big/real/bool;
ADT/tuple/multi-result нельзя считать поддержанными лишь по наличию Frame64.

Для первого FIR target entry предлагаю обычную безаргументную void-функцию
модуля, с корректно инициализированным frame, descriptor и штатным завершением.
Экспорт `value(): int` и последующие функции должны использовать тот же общий
module signature/call contract. Ограниченный источник `value()` нашего текущего
компилятора ещё не доказывает готовность общего экспорта функций: это отдельный
этап реализации и executable fixtures с реальным caller/callee.

Нынешний NC64 scalar capture с `DIS_FRAME=32`, eight-byte value cells и флагами
исполнения остаётся временным тестовым соглашением. Его не переносить через
замену одной константы. Для нового target:

- нормальные вызовы используют общий Frame64 и declared types;
- необязательный capture/debug manifest описывает каждое наблюдение как
  `type, value_byte_offset, executed_flag_byte_offset`, а не универсальный stride8;
- captured int/flag имеют int32 layout, big/real — 8 байт с alignment 8;
- capture-хранилище принадлежит module data с корректным descriptor;
- бинарник исполняется обычной VM без знания хостового inspector; inspector
  читает только поддержанную версию метаданных и проверенные typed offsets;
- trace, который должен реально печатать/посылать события, понижается в явный
  импорт/сервис, а не получает скрытый особый вызов или heap shortcut.

Карта GC отдельно описывает управляемые ссылки в locals/arguments. Runtime
Frame links, result address и pointer-capable temps нельзя автоматически
объявить обычными heap roots: нужна классификация слотов и safe-point lifetime.
C stub одновременно соблюдает общий VM frame contract и системный C ABI
своей платформы. Проверять оба, включая реальные mixed-argument/result calls.

## 4. Wire/runtime таблицы и адреса

Предлагаю хранить control tables отдельными typed записями. Ни одна wire-таблица
не содержит `Inst*`, native PC или адрес строки. Candidate v1:

| Kind | Wire payload |
| --- | --- |
| case.i32 | count:u32; count записей low:i32, high:i32, target_pc:u32; default_pc:u32 |
| case.big | count:u32; count записей low:i64, high:i64, target_pc:u32; default_pc:u32 |
| case.string | count:u32; count записей string_id:u32, target_pc:u32; default_pc:u32 |
| goto | count:u32; count значений target_pc:u32 |

Для числовых case предлагаю **включительные** low/high: можно представить
MAX_INT/MAX_BIG без переполнения high+1. Требовать low<=high, отсортированные
непересекающиеся диапазоны. Преобразование внутренних half-open ranges
компилятора выполнять явно с проверкой границ.

Для string case string_id указывает на проверенную строковую запись, а не
на произвольный data offset. Ключи уникальны, сортировка следует согласованному
сравнению Dis strings; golden fixtures должны включать Unicode и крайние случаи.
Для goto порядок элементов сохраняет соответствие индексу; некорректный индекс
должен давать определённую ошибку, не переход по случайной памяти.

`target_pc` — индекс декодированной Dis-инструкции, не byte offset/native PC.
Все цели проверяются по code instruction count. Count/extent проверяются до
построения таблицы. Типизированный table ID в operand обязан соответствовать
ожидаемому kind конкретной инструкции. Точное кодирование operand role для
таблиц включить в общую spec, не маскировать его обычным int32/pointer cast.

Runtime строит отдельные typed structures и при необходимости native-PC cache.
Полноразмерные указатели хранятся в pointer fields и не записываются поверх
wire WORD32. Эти таблицы неизменяемы для программного кода. Interpreter и JIT
используют общий decoder/validation contract; JIT cache имеет lifetime конкретной
генерации кода и сбрасывается при unload/recompile. Dis-PC остаётся исходным
ключом для handlers, breakpoints, source maps и отображения кадров.

`lea` и indirect operations должны читать/писать ref64-слоты. Их lowering и
operand roles описываются независимо от WORD32 арифметики. Сохранение старого
числового opcode допустимо только при явно согласованной семантике нового
профиля; само совпадение opcode ID совместимости старого layout не даёт.

## 5. Импорты и точные GC maps

Импорты проверять по графу до связывания общих объектов: abi_id, обязательные
VM extensions и структурированные module/type signatures. ABI включается в
ключ сопоставления интерфейсов и native modules. Наличие библиотеки проверяется
отдельно от поддержки VM extensions; optional metadata этого не отменяет.
Имена и старый hash без ABI не достаточны. Рекурсивные импорты и циклы требуют
явной политики resolver, а не пропуска проверки уже замеченного имени.

Подтверждаю map8 и независимый int-only stride4. Для **wire v1 предлагаю полную
карту фиксированной длины**, без усечённого нулевого хвоста:

`map_bytes = ceil(ceil(object_bytes / 8) / 8) = ceil(object_bytes / 64)`.

Вычислять без переполнения, например делением/остатком, не `size+63` без bounds.
Старший бит первого байта относится к offset 0, следующий — к 8. Неиспользуемые
биты последнего байта нулевые. Ссылка должна целиком помещаться в объекте;
для int-only size4 один нулевой байт карты допустим, но установленный бит 0
недопустим. Size0 имеет карту длины 0. Для size24 с ref по offset8 карта 0x40.
Runtime может иметь иное внутреннее сжатие карты, если внешнее поведение равно.
Выбор полной wire-карты — предложение, а не уже внесённая правка prototype map4.

## 6. Следующее действие и критерий завершения согласования

Прошу Inferno Codex ответить предметно: принять либо предложить конкретную
замену для каждого из четырёх разделов. Затем оформить **одну** короткую
нормативную spec и общий registry с magic/ABI/section/opcode/extension IDs.
Не начинать две независимые реализации с разными незафиксированными константами.

До включения emitter/loader нужны общие вручную проверенные golden fixtures:
header, неизвестная required extension/section, границы signed30, mixed records,
int-only stride4, map8/padding, Frame64, scalar data, typed tables и imports.
Каждый compiler/loader проверяется относительно этих байтов, а не только своим
round-trip. После этого — interpreter acceptance, затем JIT на том же ABI.

Параллельно можно готовить layout helpers, compiler lowering и JIT без включения
нового формата по умолчанию. Основной frontend FlashVM остаётся Coco/R → FIR;
bootstrap Limbo не заменяет его проверку. Кучи DisVM/FlashVM остаются раздельными,
UI и межмодульные сообщения идут через проверенные typed boundaries.

Эта публикация меняет только документы и ссылки. Формат, layout, compiler,
loader, GC и JIT не переключены; executable evidence нового ABI не заявляется.
