## 1. Контекст и проверенная база

Inferno: `experiment`,
[`25626d8dcc0ecac2a7438e3ae4c05949e3f2ca5e`](https://github.com/bhgv/Inferno-OS-bhgv/tree/25626d8dcc0ecac2a7438e3ae4c05949e3f2ca5e).
FlashVM: `master`,
[`e2d1836c9a83ada82fa81f0183cd7302959de8c1`](https://github.com/bhgv/flashVM/tree/e2d1836c9a83ada82fa81f0183cd7302959de8c1),
серия v0.1678. Её изменения касаются ввода/рисования IDE; переход Dis64 там не выполнен.

Проверенные источники FlashVM на этой базе:

- [Прямой FIR → Dis](https://github.com/bhgv/flashVM/blob/e2d1836c9a83ada82fa81f0183cd7302959de8c1/fir/v1/compiler/dis.c):
  NC64 magic 819264, `DIS_CELL=8`, `DIS_FRAME=32`, явная нормализация i32.
- [FIR → hosted tables/calls](https://github.com/bhgv/flashVM/blob/e2d1836c9a83ada82fa81f0183cd7302959de8c1/fir/v1/compiler/dis_table.c):
  восьмибайтовые ячейки и шаг карты корней, собственные слоты вызовов.
- [Рабочий DisVM host](https://github.com/bhgv/flashVM/blob/e2d1836c9a83ada82fa81f0183cd7302959de8c1/disVM/runtime/README.md),
  [подготовка host view](https://github.com/bhgv/flashVM/blob/e2d1836c9a83ada82fa81f0183cd7302959de8c1/disVM/runtime/prepare.py).
- [Собственный Limbo frontend на Coco/R](https://github.com/bhgv/flashVM/tree/e2d1836c9a83ada82fa81f0183cd7302959de8c1/compiler/limbo/frontend).
  Сохранённый C Limbo — временный bootstrap, не замена этому frontend.

Существующее решение пользователя: старые experimental NC64-бинарники можно
пересобрать. Один общий новый ABI для Inferno и DisVM предпочтительнее двух
расходящихся 64-битных профилей. Отдельная NC64 compatibility VM, конвертер
старых файлов и мост общих heap-объектов между ABI не нужны для миграции.

Архив `disvm-inferno-review-2026-10-29(2).zip` и соответствующий patch, присланные
в FlashVM, побайтно совпали с предыдущей выдачей. В их README прямо исключены
изменения формата/ABI. Три патча синхронизируют JIT/parser и добавляют проверки
копирования записей. Их тесты не являются подтверждением нового Dis64 ABI.
Не следует применять эту старую серию целиком поверх нынешнего FlashVM/master.

## 2. Краткая рекомендация

Принять направление `int32 + ref64 + big64 + binary64`, естественное выравнивание
и согласованную пересборку. Для **нового** ABI64 я рекомендую шаг GC-карты **8 байт**,
новый discriminator формата с явными version/ABI и единый источник target layout.
Численные значения нового magic/version здесь намеренно не назначены.

Рекомендация GC-map8 отличается от текущего проекта Inferno GC-map4. Это
предложение для согласования, а не уже принятое изменение `DisMapQuantum`.
Старые проектные документы остаются описанием исходного варианта до решения.

| Свойство | Рекомендация | Статус |
| --- | --- | --- |
| `byte` | 8 бит | Поддержать исходный проект |
| `int`, `WORD`, `UWORD` | 32 бита, явные signed/unsigned операции | Поддержать |
| `big`, `real` | 64 бита / IEEE binary64 | Поддержать |
| `ref`, string/list/array/chan/module reference | 64 бита, alignment 8 | Поддержать |
| GC-map quantum ABI64 | 8 байт | Предлагаемая поправка, требует решения |
| Обычная область Frame + result + temps | 64 байта, точные поля ниже | Кандидат, не активный контракт |
| Файловые индексы и operands | Ограниченные числа, не нативные адреса | Поддержать; пределы уточнить |
| Старые NC64-файлы | Явный отказ с требованием пересборки | Уже допустимое направление миграции |

Не расширять все поля до 64 бит и не описывать target через `sizeof(long)` хоста.
Не сужать все нынешние NC64-ячейки до 4 байт: ссылки, big, real и внутренние
таблицы имеют собственные размеры. Семантика FIR i32 и Limbo int остаётся 32-битной;
это не утверждение, что все числовые значения ActionScript должны стать int32.

## 3. Почему GC-map8, и когда допустимо GC-map4

Layout полей и гранулярность карты GC независимы. При alignment ссылок 8 каждая
ссылка начинается в восьмибайтовой позиции. Восемь байт без ссылки могут содержать
два int32; бит карты равен нулю. Чтобы упаковывать int32, карта с шагом 4 не нужна.

Для `int a; ref b; int c` при естественном выравнивании:

| Поле/свойство | ABI64 + map4 исходного проекта | ABI64 + map8 рекомендации |
| --- | ---: | ---: |
| offset a | 0 | 0 |
| offset b | 8 | 8 |
| offset c | 16 | 16 |
| Размер после выравнивания | 24 | 24 |
| Bitmap, старший бит соответствует offset 0 | 0x20 | 0x40 |

Map8 даёт один бит на возможный полный ref64, примерно вдвое меньшую карту и
не требует держать всегда пустыми биты вторых половин указателей. Она ближе
к нынешнему NC64 bitmap quantum DisVM, хотя весь остальной layout всё равно меняется.

Map4 тоже корректна: бит отмечает начало ссылки, вторую половину отмечать нельзя.
Плюс — единый шаг с классическим Dis и меньше изменений части старых генераторов.
Минусы — избыточные биты и дополнительные ограничения карты. Я не считаю map4
ошибкой безопасности при правильных байтовых обходах и валидации.

Предлагаемое решение: ABI32 сохраняет свой map4; новый ABI64 использует map8.
Если совместное ревью выберет map4 ради инструментов, это допустимая альтернатива,
но нужно зафиксировать её до генерации модулей и не объяснять упаковкой int32.
Внутри одного опубликованного ABI не должно быть двух неявных толкований карты.

В обоих вариантах:

- GC-карта оперирует байтовыми смещениями, не индексами `WORD **`.
- Полный указатель обязан помещаться в объекте и быть выровнен.
- Неполный последний квант допустим только без отмеченной ссылки; padding bits
  не могут указывать за объект. Допустимость усечённого нулевого хвоста карты
  должна быть определена в wire spec, а не угадана загрузчиком.
- Структура с ref получает alignment не меньше 8; её array stride кратен 8.
  Структура только с int32 не обязана получать alignment 8 из-за шага карты.
- Обновляются все mark/init/free/copy/type/JIT helpers, каналы и контейнеры.
  Одной правки `markheap` недостаточно.

## 4. Три разных контракта: файл, VM, native C

### 4.1. Формат файла

Предпочтение: новый magic, который старые загрузчики явно отвергнут, и заголовок
с явными `format_version` и `abi_id`. Точные размеры/кодирование этих полей,
обязательные флаги и правила дальнейшего расширения согласовать до реализации.
Не менять существующий файл под старым magic и не считать ABI названием backend.

Заняты и не могут обозначать новый несовместимый ABI64:

- classic unsigned/signed magic: 819248 / 923426;
- experimental NC64 unsigned/signed magic: 819264 / 923442.

Спецификация должна отдельно определить:

1. Canonical byte order для каждого фиксированного поля и scalar initializer.
   Предпочтение — сохранить действующее canonical кодирование scalar payloads,
   где это не конфликтует с новым явным заголовком. Не копировать little-endian
   SWO1/SWA1 header: это другой backend/контейнер.
2. Компактные operands и реальные диапазоны. Нынешнее signed30 кодирование —
   диапазон `-2^29 .. 2^29-1`, а не произвольный int32. Положительное прямое
   смещение такого operand ограничено `2^29-1` байтами. Внутренний предел
   `DisMaxOffset=0x7fffffff` не означает, что его можно записать этим кодированием.
   Предел layout, предел записи и предел runtime allocation — разные проверки.
3. Instruction IDs, адресные режимы, индексы Dis-PC и метаданные данных/типов.
   Сохранять opcode IDs только там, где действительно сохраняется семантика.
4. Формат ref initializer/relocations, strings и type descriptors. Нативный
   адрес, `sizeof(Inst)` и C struct padding в файл не записываются.
5. Представление nil в файле и отдельную инициализацию runtime nil. В Inferno
   `H` сейчас `(void*)-1`; нулевые байты нельзя молча признать его эквивалентом.
6. Ранний отказ для неверной версии/ABI и несовместимых импортов до ABI-зависимых
   heap/stack allocation и relocation. Для signed modules discriminator входит
   в подписываемое содержимое; это требование, не обещание готового verifier.

Не расширять автоматически все offsets/indices до 64 бит. При реальной
необходимости больших модулей отдельно версионировать соответствующее поле.
64-битное адресное пространство VM не требует 64-битной записи каждого operand.

### 4.2. Layout VM и frame

Существующий `Frame` в `include/interp.h`: `lr`, `fp`, `mr`, `t`. Кандидат для
обычного 64-битного соглашения вызова:

| Offset в байтах | Поле | Размер |
| ---: | --- | ---: |
| 0 | Frame.lr, runtime instruction pointer | 8 |
| 8 | Frame.fp, caller frame pointer | 8 |
| 16 | Frame.mr, module link | 8 |
| 24 | Frame.t, frame type | 8 |
| 32 | Адрес результата | 8 |
| 40 | STemp | 8 |
| 48 | RTemp | 8 |
| 56 | DTemp | 8 |
| 64 | Начало последующих аргументов/локальных данных | — |

Это кандидат для согласования и проверки generated stubs, не утверждение,
что все восемь slots являются обычными GC roots. Правила обхода runtime-полей,
временных значений и аргументов задаются отдельно. Даже temp с int32 имеет
восьмибайтовый запас, если по контракту этот slot может временно содержать адрес.

`REGRET`, `NREG`, `STemp/RTemp/DTemp/MaxTemp` должны следовать явному frame layout,
а не произведению `NREG*IBY2WD`, если WORD32 и ref64 различаются.

У прямого scalar FIR backend собственные entry/capture slots после Frame32.
Его `DIS_FRAME=32` нельзя просто заменить на 64, считая это готовой миграцией
обычного Limbo-вызова. Нужно отдельно описать FIR entry/result/module-call ABI,
обновить stack/data descriptors и проверить результат с native callers.

`lea`, indirect access и pointer arithmetic должны работать с ref64-слотами,
а не через WORD32. Определить их lowering/операции до включения target. `movp`
сохраняет refcount/GC семантику; это не просто восьмибайтовый `memcpy`.
`case/casec/goto`, return PC и handlers не могут хранить native PC64 в WORD32.
Файловые таблицы индексов и runtime relocation/cache надо описать раздельно.

### 4.3. Native C и debugger

Target layout не зависит от compiler host ABI, включая LP64/LLP64. C stubs,
типы результатов и смещения должны генерироваться из того же target contract.
Проверки ширин/offsets выполняются при сборке; не полагаться на комментарий
«long = 32 bits». Произвольный 32-битный host не становится исполнителем native
ref64 VM: cross-compilation и исполнение — разные обещания.

В module/type signatures учитывать ABI/version до связывания heap-объектов.
Отладчик и Loader экспортируют Dis instruction indices, source coordinates и
описанные byte offsets; нативные JIT-адреса не становятся переносимыми метаданными.
`.sbl` и наш FIR debug output пересоздаются вместе с кодом; source maps должны
ссылаться на те же Dis-PC, что интерпретатор и JIT.

## 5. Один источник layout и собственные компиляторы

Нужен один versioned target contract: размеры, alignment, размещение полей,
frame/result/temp offsets, GC quantum/bit order, wire limits и table rules.
Форма реализации — общий header/helper либо нейтральное описание с генерацией
для C и собственных компиляторов. Выбор инструмента не должен добавлять Python
или иной host generator в обязательный runtime развёрнутой IDE.

Не требуется переносить в Inferno всю FIR-библиотеку FlashVM или объединять
кучи VM. Нужны одинаковые правила и fixtures с известными байтами/offsets.
Точки согласования с FlashVM: собственный Coco/R Limbo → FIR, FIR → Dis,
hosted table/call lowering, временный bootstrap Limbo, native module headers,
loader, interpreter/JIT, debugger, `.dis/.sbl`, библиотеки и SDK.
AS1/2/3 → FIR используют тот же выбранный Dis target там, где он поддерживается;
их SWF backend и контейнер SWF не меняются этим предложением.

## 6. Последовательность реализации для следующего Codex

1. Прочитать этот документ, исходный design и compatibility. Проверить свежие
   HEAD обоих репозиториев. Не выдавать предложения здесь за уже принятое решение.
2. Зафиксировать в отдельном решении: GC-map4 или map8, новый magic/header,
   точные wire bounds, frame и FIR entry/call contract. Числа не выбирать
   независимо в двух репозиториях. Не включать ABI под старым magic.
3. Реализовать общий layout и table-driven fixtures; пока активный compiler/VM
   не переключать. Генератор нового target может работать только явно;
   неготовый загрузчик обязан отвергать его файлы.
4. Согласованно обновить собственный Limbo/FIR backend и bootstrap/stubs.
   Не считать работу только над C Limbo завершением основной компиляторной задачи.
5. Реализовать interpreter ABI64, loader, GC, calls, channels, exceptions,
   stack growth и typed tables. Выполнить чистую пересборку стандартных модулей.
6. После interpreter acceptance включать x86-64/ARM64 JIT на том же ABI;
   затем RV64. Сравнивать поведение и debug state с интерпретатором.
7. Обновить SDK, консольные инструменты, библиотечные интерфейсы и IDE;
   проверить запуск из перенесённой установленной сборки. Синхронизировать
   подтверждённые общие исправления в обе стороны с сохранением происхождения.

Старый NC64 может временно оставаться рабочим target до переключения. Это
не требование сохранять его отдельную VM после миграции. Запрещено молчаливое
переосмысление старых файлов и смешивание объектов разных ABI в одной куче.

## 7. Критерии проверки: что считать доказательством

- Layout fixtures: смешанные scalars/refs, padding, nested records, arrays,
  int-only records с четырёхбайтовым stride; позитивные/негативные GC maps.
- Раздельные проверки target layout на compiler host32/64. Реальное исполнение
  ABI64 на заявленных 64-битных платформах; модель LLP64 не заменяет Windows run.
- Wire golden bytes и read/write round trips; границы signed30 и каждого header
  field; усечённый ввод, переполнение и неверный ABI отвергаются явно.
- i32 wrap/sign/shift semantics, big64, binary64 signed zero/NaN; удалять старую
  NC64 i32-нормализацию только после соответствующей смены операций/слотов.
- Реальные ссылки выше 4 ГБ, nil, refcount/GC, record copy/move/overlap,
  stack relocation/growth, scheduler/channels, exceptions и module calls.
- Layout checks generated C stubs и реальные вызовы с аргументами/результатами
  смешанных типов. Проверить собственный FIR entry отдельно от обычного Frame.
- Case/goto/string tables, динамический Loader, source maps и breakpoints:
  одинаковые Dis-PC и состояния interpreter/JIT; повторный JIT compile/free.
- Чистая сборка модулей и SDK; полные прогоны относятся к **точному итоговому
  дереву каждого репозитория**. Публиковать hashes и границы доказательств.

`libinterp/tests/dis-layout.py` сейчас проверяет прежний prototype map4, не
активный общий runtime. Рабочие NC64-тесты, тысячи record-copy случаев и наличие
ARM64 исходников не доказывают исполнения нового ABI64 или физического ARM64.
Прототип, C harness со stubbed heap и настоящий compiler → module → VM run
нужно называть разными уровнями проверки.

## 8. Что изменено этой публикацией

Только предложение и ссылки из двух проектных документов. `dis-layout.h`,
magic/opcodes, compiler/VM/FIR/GC, форматы модулей и действующие профили не менялись.
Проверены относительные ссылки и чистота diff. Исполнительные тесты ABI не
запускались: это документационная публикация, а не реализация Dis64.
