# Скалярные библиотеки Dis64 и структурные импорты

[English version](dis64-scalar-libraries.md).

Limbo теперь выпускает полный скалярный библиотечный файл. Нативный конструктор
создаёт экземпляр по проверенным структурным запросам импортов. Сам конструктор
не вызывает `init`. Это файловая половина provider-пути; общий гостевой `LOAD`,
допуск namespace/кэша и импортирующий managed-клиент остаются отдельной задачей.

## Компиляция

`library.m`:

```limbo
Library: module {
    init: fn();
    mid: fn(n: int): int;
    leaf: fn(n: int): int;
};
```

`library.b`:

```limbo
implement Library;
include "library.m";
init() {}
mid(n: int): int {
    a := leaf(n);
    return leaf(a);
}
leaf(n: int): int { return n+1; }
```

```sh
limbo -64b -I . -o library.dis64 library.b
limbo -H -M Library library.m > library-native64.h
```

`mid(7)` возвращает9. `init` здесь обычная экспортированная функция: вызывающий
код может явно запросить и вызвать её. Загрузка/создание экземпляра кода не
исполняет. Генерация C-заголовка остаётся свидетельством ABI; классические
сигнатуры по-прежнему вычисляет сам Limbo из `.m`.

| Ключ | Метаданные | Точка входа |
| --- | --- | --- |
| `-64b` | Существующий library profile0 | Отсутствует, даже при функции с именем `init` |
| `-64c` без `init` | Существующий library profile0 | Отсутствует |
| `-64c` с реализованной `init` | Существующий executable profile1 | Прежние правила командного модуля |

Оба скалярных ключа отключают инлайнинг; добавление `-i` не меняет байты.
Классический Dis и ключи `-64`, `-64m`, `-64l` сохраняют свой смысл. Запуск
`emu -X dis64-calls -d library.dis64` намеренно отклоняется: командному старту
нужен исполняемый модуль. Выбор вызываемой функции после загрузки делает
вызывающий код, например sh; библиотечный конструктор этого не делает.

## Проверка всей библиотеки

Библиотеки и команды используют одинаковые перенос функций, Frame64, materializer
и C/JIT. Библиотечные метаданные содержат только имя, профиль и размер данных.
Фиктивной корневой функции и sentinel-точки входа на wire нет. Порядок функций
остаётся скомпилированным; функция №0 может иметь аргументы/результат, вызывать
другую функцию и вызываться из неё.

Каждой скомпилированной функции нужен объявленный экспорт. Интервалы функций
не пересекаются и покрывают весь код. Проверяются и невостребованные функции,
даже при пустой таблице запросов. Сигнатуры: void/int/big/real. Leaf-функции без
вызовов сохраняют проверенные переходы, циклы и несколько return. Функции с
вызовами линейны, завершаются RET и образуют DAG. Каждый нормальный nonvoid-return
записывает определённое значение через свой входящий указатель результата.
EXIT недопустим во всех библиотечных функциях.

Каждый caller привязывает собственный хвост результата. Выражение `return f(n)`
копирует готовый ответ через свой входящий указатель после возврата. Указатель
вызывающего кода дальше по цепочке не передаётся. Числовые преобразования
сохраняют [правила скалярного файлового пути](dis64-source-call-files.ru.md).

Пределы:256 итоговых инструкций,64 функции/дескриптора/аргумента, кадр и выходной
образ до1MiB. Карты указателей должны быть нулевыми. Данные модуля, собственные
импорты, managed-ссылки, byte-сигнатуры, обработчики, рекурсия, ветвления caller
и скрытые скомпилированные функции отклоняются. Общая managed-библиотека и
библиотека, сама импортирующая другой модуль, этим шагом не сериализуются.

Компилятор и runtime независимо вызывают dis64calllibraryinfercheck по полному
сырому образу. Records/count/image публикуются только после полного proof;
рабочая память при отказе может измениться. Прежний executable-checker и точные
сводки его допустимых модулей сохранены. Новых wire-ID нет: существующие
Dis64v1.0 ABI1, пять секций и скалярные сигнатуры version1 остаются прежними.

## Создание экземпляра по импортам

```c
Modlink *prepare64calllibrarylink(
    char *path, uchar *image, ulong bytes, int jit,
    const uchar *imports, ulong importbytes,
    const uchar *strings, ulong stringbytes);
```

`imports` и `strings` — полные payload существующих секций Imports и Strings.
Это неизменяемые заимствованные байты, а не таблицы нативных указателей. Их
формируют dis64signaturewrite, disstringpoolwrite и dis64bindingswrite из нужного
скалярного интерфейса. Для `mid` это signaturev1, результат int, один аргумент int
и строковые ID модуля `Library` и функции `mid`.

Сравниваются точное имя модуля, имя функции и полная структурная сигнатура.
Big и Real не совпадают только потому, что оба занимают8 байт. Порядок links
совпадает с порядком запросов; точные повторяющиеся запросы сохраняют старую
семантику codec. Поддерживаются 0..64 запроса,65 отклоняются до выделения памяти.
Конфликтующие повторы, отсутствующий/поздно несовпавший экспорт и повреждённые
метаданные не публикуют частичный результат сопоставления или VM-владельца.

После полного proof конструктор владеет копиями кода, Types/maps, имён модуля/
пути и JIT. Используется штатный mklinkmod; положительные ordinal-links получают
доказанные координаты экспорта. MFRAME берёт настоящий кадр provider со всеми
локальными местами. MCALL и RET — прежние обработчики runtime. Исходные буферы
образа, запросов и строк после возврата можно уничтожить.

32-битные хэши не придумываются; в Module.ext не устанавливаются фиктивные
сигнатуры. Классические хэши `.m` и отдельный [доверенный конструктор импортов](dis64-owned-imports.ru.md)
сохраняют свои контракты. Одного структурного совпадения недостаточно: runtime
обязательно доказывает код всех функций перед созданием экземпляра.

## Владение и отказы

Нужны VM exclusion, отключённый allocation monitor и совместимый нативный
WORD32/ref64 caller. Успех возвращает одну ссылку Modlink и один внешний GC-pin.
Перенесите экземпляр в размеченную VM-ячейку по обычным правилам ссылок и barrier,
затем вызовите `ptrdel(D2H(ml))`.
Отказ от ещё не опубликованного результата под тем же exclusion:

```c
ptrdel(D2H(ml));
destroy(ml);
```

Nil означает отказ/ошибку. Частичные Module, Types/maps, код/JIT, Modlink и
неудачное финальное получение pin освобождаются. После успешного ptradd больше
нет fallible-работы. MP у этой чистой библиотеки отсутствует. Экземпляр удерживает
модуль, пока links/кадры используют его код и Types.

API не читает namespace, не регистрирует кэш и не разрешает гостевой LOAD.
`path` — копируемая метка. Здесь нет допуска произвольных C-манифестов, смешения
legacy/native экземпляров или concurrent revocation. Инициализация динамических
C-модулей и managed-граф импортов остаются за этой границей.

## Проверки

```sh
python3 utils/tests/dis64-library-files.py --limbo /host/limbo
python3 utils/tests/dis64-library-check.py --limbo /host/limbo
for control in module signature entry atomic; do
    python3 utils/tests/dis64-library-files.py --limbo /host/limbo --control "$control"
done
```

Применяются прежние CC/NATIVE64_ARCH/NATIVE64_RUNNER/NATIVE64_CFLAGS. Только
построение/освобождение под host ASan/UBSan:

```sh
ASAN_OPTIONS=detect_leaks=0 \
NATIVE64_CFLAGS='-O1 -g -fno-strict-aliasing -fsanitize=address,undefined -fno-sanitize-recover=all' \
python3 utils/tests/dis64-library-files.py --limbo /host/limbo --materialize-only
```

14 полных библиотек покрывают пустую/void-функцию, вызовы функции №0 в обе
стороны, вложения, переходы/циклы, int/Big/Real, смешанные выровненные аргументы
и ошибки. На x64 и ARM64/Linux QEMU проходят по336 scheduler-root: четыре
сочетания C/RX caller/provider, реальное расширение стека и кванты1/3/1000.
Нормальные запуски требуют успешного настоящего RX-dispatch; ошибочная инструкция
может использовать C fallback, в том числе без RX-entry при постоянном нулевом
делителе. Выбор JIT не означает машинный код для каждой инструкции. Проверяются биты ответа, уничтожение
входных буферов, каждое выделение конструктора и отказ финального pin. Внешний
импортирующий caller — доверенный тестовый C-код; provider целиком взят из файла.

10 неподдержанных исходников не выпускают payload. Сырой gate покрывает74 случая
с независимым Python-анализом caller/leaf/DFS и canary-выходами. Три отключения
обнаруживают потерю return-proof функции №0 и защиты от прямой/взаимной рекурсии.
Ещё четыре обнаруживают потерю имени модуля, полной сигнатуры, запрета точки
входа и атомарности сопоставления. Host ASan/UBSan для конструктора/сырого proof
и UBSan runtime x64/ARM64 проходят. Ограниченные GC/OS-стыки fixture и прежний
runtime-ASan unwind остаются явно отделёнными.

Полные консоли сохраняют по56 прежних executable-file OS-root и отклоняют по28
библиотечных командных запусков. Это регрессия/отказы, а не новый положительный
полный LOAD библиотеки. AWM, Android/Bionic GUI и рабочий APK пока не подтверждены.
[Отчёт INFERNO-0179](dis64-inferno-scalar-library-report.md).
