## Рекомендация со стороны Inferno

Предложение технически здравое. Рекомендую взять его за основу общего Dis64 и адаптировать Inferno к согласованному контракту. Не требуется переносить весь FIR в Inferno или переделывать собственный frontend FlashVM под upstream Limbo.

Поддерживаю:

- `int/WORD/UWORD` 32 бита, `ref` 64 бита, `big` 64 бита, `real` IEEE binary64.
- Естественное выравнивание; ссылки имеют alignment 8.
- GC-map8 для нового ABI64, сохранение map4 существующего ABI32.
- Новый discriminator с явными format version и ABI; старые classic/NC64 magic не переиспользовать.
- Пересборку экспериментальных NC64-модулей вместо отдельного слоя бинарной совместимости.
- Единый versioned target contract и общие проверочные fixtures для независимых реализаций.
- Проверку нового исполнения сначала в интерпретаторе, затем включение x86-64/ARM64 JIT на том же ABI; подготовку JIT можно вести параллельно. RV64 следует после приоритетных архитектур.

Это рекомендация Inferno в ответ на предложение, а не утверждение о двустороннем принятии окончательной wire specification.

## Поправка к прежнему проекту Inferno: GC-map8

Прежний выбор map4 не следует обосновывать упаковкой int32. Layout данных и гранулярность карты независимы.

При alignment ссылок 8 map8 отмечает каждый возможный полный ref64 одним битом. Два int32 могут занимать восемь байт с нулевым битом. Объекты без ссылок могут иметь alignment и array stride 4.

Для `int a; ref b; int c` offsets 0/8/16, размер 24 и map8 bitmap 0x40 при старшем бите для offset 0 корректны. Map4 также можно реализовать корректно, но она здесь избыточна. Теоретически карты map8 примерно вдвое компактнее; фактическое ускорение GC требует измерений.

В прототипе Inferno пока остаётся map4. Замена требует согласованной правки layout, карт, всех GC/RC/type/copy helpers и тестов, а не одной константы.

## Что нужно согласовать до реализации формата

### 1. Базовый профиль и расширения DisVM

DisVM является дальнейшим расширением Dis/Inferno. Общий базовый Dis64 должен выполняться обеими реализациями при наличии нужных библиотек. Расширенный модуль DisVM может требовать возможностей, которых нет в Inferno.

Предлагаю описать механизм обязательных расширений: их идентификаторы, версии и правила совместимости. Неизвестное обязательное расширение должно приводить к отказу до исполнения, а не к попытке угадать смысл opcode или layout. Конкретное кодирование списка/битов ещё предстоит выбрать; номера независимо не назначаем.

Следует разделить:

- версию wire format;
- идентификатор layout/calling ABI;
- требуемые расширения команд, типов и runtime;
- интерфейсы импортируемых библиотек.

Единый abi_id сам по себе не доказывает, что Inferno реализует все расширения DisVM. Нужны общие правила распределения opcode/extension namespace, чтобы избежать коллизий.

### 2. Совместимость импортов

Одинаковый layout файла не гарантирует выполнения при отсутствующей библиотеке или несовместимой сигнатуре. ABI/version и необходимые возможности должны проверяться согласованно по графу зависимостей до связывания несовместимых объектов.

Нужно определить, как ABI участвует в module/type signatures и сопоставлении native modules. Одинаковое имя модуля и старая сигнатура недостаточны.

### 3. Таблицы, адреса и вызовы

До включения target следует окончательно описать:

- `lea`, indirect access и операции с pointer64 отдельно от int32;
- файловые и runtime-представления `case/casec/goto`;
- return PC, handlers и relocation/cache без усечения указателей;
- обычный Limbo Frame/result/temp layout;
- собственный FIR entry/result/capture/module-call contract;
- правила root scanning и lifetime временных слотов.

Предложенный Frame64 разумен как кандидат. Однако совпадение его размера с 64 байтами не делает его системным C ABI. C-переходники x86-64/ARM64 должны соблюдать соглашение соответствующей ОС/платформы. Не все поля Frame и temps являются обычными GC roots.

### 4. Точная wire specification

Нужны порядок и кодирование полей заголовка, mandatory/reserved flags, byte order, диапазоны operands/indices, правила дальнейшего расширения и эталонные байты.

Особенно важно разделять предел layout, предел signed30 operand и предел runtime allocation. Для существующего signed30 диапазон составляет `-2^29 .. 2^29-1`.

Для карт определить длину, допустимость усечённого нулевого хвоста, порядок битов и нулевые padding bits. При map8 четыре байта int-only объекта допустимы, но ссылка в неполном восьмибайтовом кванте недопустима. Размер карты рассчитывается с округлением вверх, если выбрано полное представление.

Nil initializer в файле и runtime nil должны быть описаны отдельно. Это не повод менять текущую nil-семантику молча.

## Предлагаемый следующий обмен

Со стороны FlashVM полезен ответ по четырём решениям: механизм расширений, точный header/discriminator, FIR entry/call contract и wire/runtime таблицы.

Следующий совместный результат — короткая нормативная specification и общий набор fixtures: смешанные записи, int-only stride4, карты, frame offsets, scalar payloads, граничные operands, импорты и отказ при неизвестном ABI/extension. Для каждой реализации нужны независимо проверенные ожидаемые байты и offsets, а не только round-trip через один и тот же код.

Числа magic/version/ABI/extension согласовать в одном месте до включения emitter/loader. В Inferno сначала реализовать явный target и интерпретатор, затем нативные быстрые пути плюс C handlers на общем контракте.

Основной путь собственного Limbo FlashVM — Coco/R → FIR. Upstream C Limbo/iyacc остаётся временным bootstrap; его успешные тесты не заменяют проверку собственного compiler path.

## Границы текущей готовности

Старая трёхпатчевая серия JIT/parser/record-copy не реализует Dis64. Не следует применять её целиком поверх нового FlashVM/master без отдельного ревью.

Наличие 173/173 JIT+C входов и 166/173 guarded native commands на прежних layouts не является процентом готовности нового ABI. NC64-прогоны и тысячи record-copy случаев не доказывают исполнения нового Dis64; ARM64 emitter/harness не заменяет запуск на ARM64 host.

Этот ответ изменяет только документацию. Активный layout, magic, loader, compiler, GC и JIT этой публикацией не переключаются. Исполнительные тесты нового ABI не заявляются. Tk/security/crypto и JIT MIPS/SPARC/PowerPC не входят в предлагаемые изменения.
