# Структурные скалярные импорты через ILOAD

[English version](dis64-scalar-iload.md).

Инструкция VM `ILOAD` получила явный маршрут к [загрузчику библиотек через
namespace](dis64-scalar-namespace.ru.md). Теперь проверяется цепочка самой
инструкции, чтения файла, проверки доступа, полного доказательства библиотеки и
последующего вызова. Импортирующий модуль в этой проверке пока строится из
доверенных native-метаданных. Допуск импортирующего Limbo-файла этим изменением
ещё не реализован.

## Подготовка интерфейса

```sh
limbo -H -R -M Library library.m > library-native64.h
limbo -64b -o library.dis64 library.b
```

В проверенном native-конструкторе вызывающего модуля:

```c
#include "library-native64.h"
Native64ImportRequest tables[] = {
    {limbo_native64_Library_scalar_imports,
     limbo_native64_Library_scalar_strings,
     sizeof(limbo_native64_Library_scalar_imports),
     sizeof(limbo_native64_Library_scalar_strings)}
};
if(!install64callimports(caller, tables, nelem(tables), 1))
    return 0; /* Освободить неопубликованный caller штатным владельцем. */
```

`caller` должен быть ещё не опубликованным, не зарегистрированным в кэше native
модулем с единственным владельцем и `native64typedlea8step`. Наличие старой LDT или
установленной структурной таблицы запрещает повторную установку. Заранее должен
быть выбран режим запуска `dis64-calls`. Имя файла и его содержимое этот режим не
выбирают. Последний аргумент0/1 задаёт запрос JIT для загружаемой библиотеки;
актуальный `dontcompile` повторно проверяется после файлового ввода.

Все таблицы проверяются до выделения и публикации. Один блок памяти содержит
описатели и собственные копии Imports/Strings. После успеха исходные буферы можно
освободить. При отказе, включая ошибку выделения, оба поля Module остаются пустыми.
Пределы:64 таблицы,64 функции/аргумента в таблице,1МиБ на payload и8МиБ на весь
блок. Ноль таблиц недопустим; таблица с нулём запросов допустима.

API предназначен для доверенного конструктора. Он проверяет запросы, а проверка
кода вызывающего модуля, карт корней и операндов остаётся обязанностью конструктора.
Это ещё не разрешение исполнять произвольные CODE или управляемые данные файла.
В Module добавлены два внутренних поля: владелец запросов и доверенный callback.
Нужна полная пересборка runtime. Frame64, Modlink, wire-формат Dis64, публичные ID
и версия сигнатуры не меняются.

## Загрузка и вызов

Средний операнд `ILOAD` выбирает **таблицу**. Затем `MFRAME`/`MCALL` выбирают
функцию загруженного экземпляра по
`LIMBO_NATIVE64_IMPORT_Library_<имя>`. Индекс таблицы и индекс функции различаются.
Структурная сигнатура берётся из `.m`; старый32-битный хэш её не заменяет.

Источник `ILOAD` — обычная String с путём. Приёмник должен быть mapped-корнем
модуля, установленным проверенным конструктором. Отрицательный или слишком большой
индекс вызывает `exModule` до файлового ввода. Правильный индекс запускает новое
чтение без кэша: release/isave, acquire/irestore, проверку доступа, сопоставление
всего интерфейса и проверку всех функций библиотеки.

До публикации результата сохраняется временный GC pin. `ILOAD` отмечает и
публикует новый экземпляр, снимает pin и освобождает прежнего владельца приёмника.
Повторная загрузка действительно заменяет старый экземпляр. Обычный отказ загрузки
записывает H и также освобождает прежнего владельца. Ошибочный индекс оставляет
приёмник прежним. Функция init автоматически не вызывается. `$Sys`/`$self` не
входят в этот маршрут библиотек. Модули без установленного callback используют
прежние пути классических импортов и доверенных встроенных модулей.

Блок запросов принадлежит Module и освобождается в `freemod`. Во время отпущенного
VM exclusion его удерживает текущий контекст. Глобальной регистрации таблиц и
заимствованных указателей на память компилятора нет.

## Проверка

```sh
python3 utils/tests/dis64-library-namespace.py --limbo /host/limbo --iload
for control in copy pin route; do
    python3 utils/tests/dis64-library-namespace.py \
        --limbo /host/limbo --iload --iload-control "$control"
done
```

Переменные CC/NATIVE64_ARCH/NATIVE64_RUNNER выбирают ARM64/Linux QEMU. Для ASan/UBSan
нужно добавить `--materialize-only` и sanitizer-флаги в NATIVE64_CFLAGS: этот режим
проверяет установку и освобождение без исполнения инструкций VM. Прежнее ограничение
runtime-ASan при раскрутке ошибок остаётся открытым.

Матрица дважды исполняет `ILOAD` с разными таблицами: сначала пустые запросы,
затем полный интерфейс из `.m`, после чего MFRAME/MCALL. Проверяется число
связанных функций каждого экземпляра.
Проверяются четыре сочетания C/RX вызывающего модуля и библиотеки, обычный и растущий
стек, кванты1/3/1000, точные результаты и ошибки библиотеки, отказ открытия/доступа,
оба неверных индекса. Исходные буферы интерфейса отравляются до исполнения. Между
инструкциями временных pin нет; после завершения освобождаются экземпляры, String
пути, запросы, Types, JIT и файловые дескрипторы. Отдельно проверяются64 таблицы,
пустые запросы, ошибка поздней таблицы и ошибка выделения.

14 интерфейсов/библиотек дают1680 запусков на платформу. Две независимые правки `.m`
— отсутствующий неиспользуемый экспорт и несовпадение Big/Real — добавляют240
запусков отказа. Три контрольных запуска намеренно убирают копирование, снятие pin
или маршрут и требуют семантический exit10 без срабатывания sanitizer/UB.

Транспорт namespace, predicate доступа, ASCII-преобразование пути и поддержка
пула/коллектора ограничены тестовыми реализациями. Обработчик ILOAD, загрузчик,
планировщик, вызовы/возврат, освобождение ссылок и принятые native leaf исполняются
из production-кода. Это ещё не проверка конкурентной ФС/GC, допуска клиентского
Limbo-файла, Android/Bionic, AWM или рабочего GUI APK.

Продолжение: [файловый Limbo-клиент](dis64-scalar-clients.ru.md) больше не требует
C-описания вызывающего кода для ограниченной линейной команды. Есть положительные
full-OS запуски x64/ARM64; общий managed-клиент этим ещё не поддержан.
