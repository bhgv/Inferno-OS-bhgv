# Нативный клиент с собственными таблицами импортов

[English version](dis64-owned-imports.md).

В [предыдущей серии](dis64-typed-external-calls.ru.md) тела клиента получались
из Limbo, а его Module вручную собирал тестовый C-код. Теперь этот клиент целиком
собирает конструктор: функции, карты, экспорты, локальные вызовы и таблицы импортов.
Поставщик строится независимо.

## Исходник

Обычный `provider.m`:

```limbo
Provider: module {
    count: fn(n: int): int;
};
```

Клиентская библиотека с внешним и локальным вызовами:

```limbo
implement Client;
include "provider.m";
Client: module {
    fresh: fn(p: Provider, n: int): int;
    local: fn(p: Provider, n: int): int;
};
fresh(p: Provider, n: int): int {
    first := p->count(n);
    second := p->count(first);
    return second;
}
local(p: Provider, n: int): int {
    return fresh(p, n);
}
```

Переносятся обе функции библиотеки. Входная функция ей не нужна; автоматического
вызова init нет. Закрытые C-таблицы берутся из диагностики компилятора и отдельных
проверок `.m`. Обычный выход компилятора остаётся старым Dis.

## Что теперь строит конструктор

В Native64ModuleSpec добавлены `tables`/`ntables`. Каждая Native64ModuleTable
содержит массив запросов Native64ModuleImport: имя, существующую32-битную сигнатуру,
геометрию нативной области аргументов и карту ссылок. Эта геометрия не зависит
от дополнительных локальных переменных поставщика. Загружать поставщика или
знать адрес его кода при сборке клиента не требуется.

Конструктор копирует Module.ldt: массив таблиц с завершающим nil, каждый массив
Import с завершающим nil, имена и хэши. Дескрипторы областей аргументов и карты
тоже принадлежат модулю; они следуют за дескрипторами функций в Module.type.
Данные остаются под номером0, функции — index+1. Структуры Module/Frame и публичные
Dis64/ISA/Sys ID не меняются.

В Native64ModuleSite добавлены external/table/modulemode/moduleoffset. Для
локального вызова новые поля нулевые, target — индекс функции. Для внешнего
вызова target — номер запроса в таблице table. Оба вида вызовов используют общую
атомарную подготовку кода. Координаты переменной модуля должны указывать на
полную ссылочную ячейку FP/MP, отмеченную картой. Тип модуля и совместимость
семантического ABI остаются доказательствами доверенного компилятора.

Пределы:64 непустые таблицы,4096 запросов суммарно, прежние ограничения функций,
кода и32MiB совокупной геометрии. Область аргументов имеет размер64..65536,
выравнивание8, точную карту и не содержит корней в служебном заголовке кадра.
Индексы таблиц/импортов и роль переменной модуля проверяются до выделений памяти.
Частичные таблицы, имена, дескрипторы, код, экспорты, MP и JIT имеют владельца
до успешной публикации либо полной очистки. Исходный MP незарегистрированного
модуля сохраняет прежнее закрепление владельцем.

## Штатное связывание

В контексте VM с обычной обработкой ошибок, после построения обоих модулей:

```c
provider.module->ref++; /* linkmod забирает эту дополнительную ссылку. */
ml = linkmod(provider.module, client.module->ldt[0], 1);
if(ml == H)
    return 0;
/* Поместить ml в видимый GC корень VM до дальнейшей собирающей работы. */
```

Существующий linkmod сопоставляет имена/хэши всей таблицы и клонирует MP.
Он удерживает частичный экземпляр и временные корни при ошибках, забирает
входную ссылку Module на всех путях и повторно поднимает ошибки выделения памяти.
Отказ на последнем импорте освобождает уже построенные части. MFRAME/MCALL
при исполнении берут настоящий кадр и цель связанного экспорта.

Оба guard владельца должны оставаться живыми, пока используются модули и
заимствованные таблицы. Копирование guard запрещено проверкой идентичности;
clear отказывает при живых экземплярах/стеках. Контракт рассчитан на доверенный
последовательный C-код. Concurrent revocation, эпохи lifetime и допуск в кэш он
не добавляет. Совпадение старого хэша само по себе не разрешает смешивать
старый32-битный и новый нативный модуль.

## Проверки

```sh
python3 utils/tests/native64-typed-imports.py --limbo /path/to/limbo
```

Проверка включена в native64-port.py. Для ARM64/Linux QEMU используются прежние
CC/NATIVE64_ARCH/NATIVE64_RUNNER. Конструктор и связывание под ASan/UBSan:

```sh
ASAN_OPTIONS=detect_leaks=0 \
NATIVE64_CFLAGS='-O1 -g -fno-strict-aliasing -fsanitize=address,undefined -fno-sanitize-recover=all' \
python3 utils/tests/native64-typed-imports.py --limbo /path/to/limbo --materialize-only
```

Из отдельного исходника без loader переносятся все18 функций/экспортов:
33 внешних вызова и один локальный. Независимый старый Dis и проверки `.m`
дают23 импортные сигнатуры и геометрию аргументов. В интерфейсе сохраняются
семь неиспользованных leaf-объявлений; их геометрия также получена через `.m`,
без тел поставщика. Инструкции и хэши экспортов проверяются по настоящему Dis.

На x64 и ARM64/QEMU проходят по960 случаев через три модуля:768 обычных,
48 с циклом,48 с локальной обёрткой и96 с ошибкой после управляемого результата.
Тестовый внешний C-модуль вызывает экспорт клиента. Полные клиент и поставщик
получены конструктором. Исполняются штатные linkmod/MFRAME/MCALL/RET, клонирование
и очистка, все четыре пары C/RX, рост стека, кванты1/3/1000 и два входа.
Проверяются простые значения, nil, локальные/унаследованные результаты,
возврат к исходному MP и полный баланс памяти/закреплений. Строки/списки здесь
остаются непрозрачными графами с проверкой владения.

Проверены все позиции отказа выделения памяти в шести вариантах конструктора:
93/94 для одной таблицы без MP,140/141 для двух таблиц без MP и142/143
для двух таблиц с закреплённым MP, соответственно C/JIT. Десять неверных
описаний отклоняются без выделений. Проверены вторая таблица, независимость
скопированных имён/хэшей/карт и построение вызова через переменную модуля в MP.
Последнее подтверждает сборку; исполняемые исходные клиенты используют FP.
Штатный linkmod отклоняет отсутствующий/неверный последний импорт и очищает
все четыре позиции отказа при клонировании. Три активных контроля отключают
границу таблицы, роль корня и равенство хэшей; принимается точная семантическая
ошибка. ASan/UBSan конструктора/связывания и UBSan исполнения x64/ARM64 проходят.
Прежнее ограничение runtime-ASan при размотке стека остаётся открытым.
GC/OS-стыки теста ограничены; доказательства concurrent GC здесь нет.

Прежние host-проверки полного модуля960 и внешних тел912 с активными контролями
также проходят. Впереди общий managed writer/loader, допуск load и namespace/кэша,
оставшиеся операции с кучей и Android GUI. Инициализация динамических C-модулей
этим тестом не проверяется. Старые scalar/Sys/file-пути сохраняют свои возможности.
Нового запуска AWM, Bionic/Android или готового APK эта серия не подтверждает.

Отдельный [скалярный файловый путь из Limbo](dis64-source-call-files.ru.md) теперь
подаёт исходные программы в существующий raw call-file loader. Общая managed-
сериализация импортов остаётся отдельной задачей.
