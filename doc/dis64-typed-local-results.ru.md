# Локальный результат и вычисления после CALL

[English version](dis64-typed-local-results.md).

После [вызовов-посредников](dis64-typed-forwarding.ru.md) добавлена запись
результата в собственную переменную caller и перенос продолжения функции:
вычислений, ветвлений и циклов после CALL.

```limbo
implement Local;
Local: module {
    count: fn(n:int):int;
    relay: fn(n:int):int;
    chain: fn(n:int):int;
};
count(n:int):int {
    total:=0;
    while(n>0){total+=n;n--;}
    return total;
}
relay(n:int):int {
    v:=count(n);
    if(n<0)return v-1;
    return v+1;
}
chain(n:int):int {
    v:=relay(n);
    return v+2;
}
```

Проверки с хостовым Limbo этой ветки:

```sh
python3 utils/tests/native64-typed-local.py --limbo /path/to/host/limbo
python3 utils/tests/dis64-typed-local-unit.py
```

Для ARM64/Linux используются обычные CC, NATIVE64_ARCH и NATIVE64_RUNNER.
Оба набора включены в native64-port.py. Получить частный отчёт можно так:

```sh
LIMBO_DIS64_TYPED=1 LIMBO_DIS64_TYPED_LOCAL=1 \
    /path/to/host/limbo -i -o Local.dis Local.b
```

Существующий `-i` отключает встраивание функций. Local.dis остаётся обычным
классическим байткодом; это ещё не команда сборки управляемого Dis64 или APK.

## Что поддержано

Один полный блок вызова должен начинаться с первой инструкции функции:
FRAME, аргументы в порядке объявления, привязка результата и CALL в точное
начало известной локальной функции. Сверяются дескриптор, виды и раскладки;
все потомки должны переноситься, циклы/чрезмерная глубина отклоняются.
В первом варианте виды результатов caller и callee должны совпадать.
Результат пишется в типизированное прямое FP-поле; MP, aggregate и varargs
пока отклоняются.

После вызова работают прежние типизированные команды, включая переходы.
Переход не может войти или вернуться в подготовку вызова, даже в FRAME.
Второй вызов в том же теле, вычисления перед первым FRAME, void и MCALL
пока не поддержаны. Подготовка аргументов и адреса локальной переменной
не считается определением результата самой функции: все достижимые RET
по-прежнему требуют настоящей записи результата на каждом входящем пути.

## Адрес в живом стеке

Доверенный сборщик неопубликованного Module выбирает новый
native64typedlea8step через существующий cstep. Форматы Module/Frame
не меняются, файл не может выбрать этот callback своим флагом.
Привязка выполняется до обычного decode/JIT. В обоих режимах C/RX сама
привязка исполняется на C; нового аппаратного LEA здесь нет.

У частного LEA незадействованное среднее поле хранит размер OR бит16
для ссылки:1 для byte,4 для Word,8 для big/real,24 для ссылки.
Проверяются геометрия Word32/ref64, границы/выравнивание поля caller,
его карта GC, подготовленный указатель в служебном поле40, соседство
кадров либо переход в новый extent, полный размер и дескриптор callee.
После проверки все8 байт адреса записываются в поле32 callee.
Обычный Word32 LEA остаётся прежним. Обход через уже декодированный JIT
отклоняет существующая защита переведённого владельца.

Предпосылка — доверенные живые VM-кадры/Type под синхронным исключением VM.
Метаданные неизменны и удерживаются обычным стеком/Module; отдельный pin,
конкурентный протокол/ABA и аутентификация чужих указателей не добавлены.
Точный смысл поля доказывает компилятор, карта GC задаёт только роль корня.
Callback не выделяет память и не приобретает владение.

## Отчёт и проверки

Для локального caller используется частная схема inferno-typed-local-v1.
Поле tail сохраняет идентификатор callee, local содержит
[относительный_PC_CALL,нативное_смещение,размер_OR_бит_ссылки].
В шестипольной инструкции64 означает запись аргумента через подготовленный
кадр,128 OR контракт — локальную привязку. Прежние контракты листовых
возвратов сохраняются. native64typedlocalcode проверяет весь код до изменения
выхода и переносит переходы продолжения в реальные позиции Module.
Согласованность Type/entry/ordinal обеспечивает доверенный сборщик;
вход и выход должны быть раздельными. Это не допуск произвольного образа.

На каждой из x64 и ARM64/Linux QEMU проходят288 исходных запусков шести видов
результата с C/RX, вложенностью, ростом стека и разными квантами/значениями.
Обе ветви caller выполняются. Ещё96 частных fault-injection случаев заменяют
первую инструкцию продолжения на деление на ноль после получения ссылки:
внешний результат не меняется, очистка стека освобождает все локальные корни.
Это проверка ошибки, не дополнительная возможность исходного языка.

1536 повреждённых привязок на архитектуру отклоняются до изменения адреса,
результата и PC, без аллокаций. Проверены чужой cstep и обход через decoded JIT.
8 отказов адаптера сохраняют выход побайтно. Два удалённых условия runtime
и два условия компилятора ловятся точными смысловыми отказами; crash/timeout/
sanitizer failure успехом не считаются. Host compiler/core проходят ASan/UBSan,
ARM64 core и runtime — UBSan. Прежнее ограничение runtime-ASan unwind открыто.

Здесь String/list identity передают непрозрачные владеющие графы; настоящие
операции со строками/списками/Unicode/GC проверяет отдельный прежний набор.
Конкурентный GC и планировщик ОС в ограниченном runtime-тесте не запускаются.

Обычный AWM остаётся14/346, одинаковый `-i` —17/380. Сохранены байты16 исходников,
376 раскладок и191 прежнего частного образа. Оба файловых профиля по-прежнему
отказывают управляемому модулю этого набора. Общие вызовы, writer/loader
и старт Android GUI ещё впереди; Android/Bionic, AWM и готовый APK не заявляются.

Multiple calls, prefix computation and void results: [dis64-typed-multiple-calls.ru.md](dis64-typed-multiple-calls.ru.md).
