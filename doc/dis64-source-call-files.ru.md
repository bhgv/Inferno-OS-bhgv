# Из Limbo в исполняемый Dis64-файл с вызовами

[English version](dis64-source-call-files.md).

Новый ключ `limbo -64c` выпускает полный скалярный модуль с корневой функцией
и вызываемыми функциями для существующего загрузчика `dis64-calls`.
Образ проверяется по собственным байтам перед записью и повторно при загрузке.
C-таблицы компилятора или нативные адреса при исполнении не передаются.

## Пример

Файл `calls.b`:

```limbo
implement Calls;
Calls: module {
    init: fn();
    sum: fn(n: int): int;
};
init() {
    first := sum(7);
    second := sum(first);
}
sum(n: int): int {
    total := 0;
    while(n > 0) {
        total += n;
        n--;
    }
    return total;
}
```

Нативный host-компилятор и экспериментальный консольный эмулятор WORD32/ref64:

```sh
limbo -64c -o /path/to/inferno/programs/calls.dis64 calls.b
emu -v -r /path/to/inferno -c 1 -X dis64-calls -d /programs/calls.dis64
```

`-c 0` выбирает C-исполнение. Ключ `-64c` сам отключает инлайнинг; добавление
`-i` сохраняет те же байты. Старые `-64`, `-64m`, `-64l` и обычный Dis сохраняют
свой смысл. Без явного выбора `dis64-calls` такой файл по-прежнему отклоняется.

Пример ничего не печатает через Sys. Консоль сообщает завершение и освобождение
процесса; второй вызов даёт406, что отдельно проверяет файловый runtime-тест.
Импорты Sys в этом профиле не нужны и не допускаются.

Пример для `big`:

```limbo
implement Wide;
Wide: module {
    init: fn();
    twice: fn(n: big): big;
};
init() {
    n := -3;
    wide := big n;
    answer := twice(wide);
}
twice(n: big): big {
    return n+n;
}
```

В сыром verifier добавлено правило преобразования `int` в `big` в корневой
функции; правило `int` в `real` уже существовало. Проверяются виды источника
и назначения, а также определённость источника в кадре. Преобразования внутри
вспомогательных функций остаются ограничены прежним доказательством leaf-кода;
все числовые сочетания этим шагом не открываются.

## Границы

Корень — экспортированная `init: fn()` без результата и аргументов. Его код
линейный, с несколькими вызовами и поддерживаемыми числовыми операциями.
Вызываемые функции — экспортированные скалярные leaf-функции: допустимы
проверенные ветвления, циклы, несколько возвратов и арифметические выражения
в return. Сигнатуры используют void/int/big/real; void-аргументы недопустимы.

Вызовы из leaf-функций, переходы корня, данные/импорты модуля, ссылки,
byte-сигнатуры, обработчики и скомпилированные скрытые функции отклоняют весь исходник.
Корень должен содержать вызов. Для каждой скомпилированной функции требуется
соответствующий объявленный экспорт. Неявного открытия скрытых функций нет.

Пределы producer:256 итоговых инструкций,64 функции/дескриптора,64 аргумента,
кадр до1MiB, образ до1MiB. Сырой proof накладывает дополнительные ограничения
локальных мест, инициализации и ресурсов. Поэтому корректный Limbo за пределами
этого подмножества может быть отклонён.

Используются уже существующие Dis64 v1.0/ABI1 и секции Module/Code/Types/Exports/
Strings, скалярные сигнатуры version1 и старые ISA-операнды. Новых публичных
ID, tags, extensions или версий формата нет. Ключ CLI выбирает producer Inferno.

## Перенос и загрузка

Writer использует typed multi-call lowerer и нативные скалярные раскладки.
Init ставится первым; функции, переходы и вызовы получают новые координаты.
К каждому кадру добавляются две восьмибайтные ячейки: временное место выражения
и канонический хвост результата вызова. Подготовленный кадр получает адрес
хвоста; после возврата значение копируется в исходную локальную переменную.
Арифметический return сначала вычисляет значение во временное место, затем
делает типизированную запись через адрес в байте32. Переходы leaf-функций
учитывают вставленные инструкции. RET корня становится EXIT.

Готовый контейнер целиком проверяет dis64callinfercheck. По сырым байтам заново
выводятся числовые локальные места и проверяются каталог, аргументы,
инициализация, принадлежность кадров, результаты и возвраты. Только затем
вызывается Bwrite. Отказ исходника/proof не публикует payload образа. Это
семантическая проверка, а не обещание транзакционного rename при ошибках I/O.

Штатные readmod/parsemod повторяют сырой proof и создают собственный код и
дескрипторы. Сохраняются отдельный выбор режима при старте, проверки профиля
кэша, callbacks допуска и C/JIT. [Доверенный конструктор импортов](dis64-owned-imports.ru.md)
сохраняет свой контракт; его C-метаданные файловым разрешением здесь не служат.

## Воспроизведение

```sh
python3 utils/tests/dis64-source-calls.py --limbo /path/to/limbo
python3 utils/tests/dis64-source-calls-unit.py
python3 utils/tests/dis64-source-call-boot.py \
    --limbo /path/to/limbo --emu /path/to/emu --root /path/to/inferno
```

Для ARM64/Linux QEMU используются прежние CC/NATIVE64_ARCH/NATIVE64_RUNNER,
а у полного boot-теста — `--runner`. Все три проверки включены в native64-port.py.
Для writer IR под ASan:

```sh
ASAN_OPTIONS=detect_leaks=0 \
NATIVE64_CFLAGS='-O1 -g -fsanitize=address,undefined -fno-sanitize-recover=all' \
python3 utils/tests/dis64-source-calls-unit.py
```

Шестнадцать программ покрывают цепочки вызовов, два аргумента, циклы,
перенумерацию переходов/возвратов, init после helper, int/big/real/void,
отрицательные числа, границы int32 и ошибки в корне/leaf. Независимый Python
разбирает реальные секции и сверяет код/сигнатуры с исходными отчётами и своим
call-oracle. Выход с/без `-i` одинаков; обычный Dis побайтно совпадает с прежним
компилятором при одинаковом пути исходника и ключах.

На x64 и ARM64/QEMU все16 файлов проходят настоящий readmod/кэш, короткие чтения,
допуск, планировщик, C/JIT и очистку. По очереди ломается каждое выделение памяти
чтения/разбора/конструктора. Проверяются биты результатов, включая преобразование
границ int32 в big. Восемь повреждённых образов отклоняются; десять неподдержанных
исходников не выпускают payload. Прежние inference9/30/312 и3343 catalog-bound
случая проходят. Активные контроли обнаруживают отключение финального proof,
неверную привязку результата, утечку таблицы координат и неверные виды conversion.

В пересобранном полном эмуляторе каждой архитектуры проходят32 настоящих OS-root:
28 нормальных завершений и четыре освобождения после zero divide, в C/JIT.
Числовые результаты проверяет отдельный файловый gate; boot проверяет реальный
старт, worker и retirement. Host-компилятор/writer IR проходят ASan/UBSan,
файловый runtime — UBSan x64/ARM64. Полная консоль собирается с обычными
целевыми флагами. Прежнее ограничение runtime-ASan на размотке стека и
ограниченные GC/OS-стыки тестового gate остаются явно отделёнными.

Это рабочий скалярный путь исходник → файл → консоль x64/ARM64 Linux QEMU.
Общий managed-граф клиента/импортов, загрузка зависимостей, операции с кучей
и Android GUI остаются впереди. Запуск AWM, Bionic/Android и готовый APK
этой серией не подтверждены.
