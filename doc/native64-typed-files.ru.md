# Checked Limbo LOAD → файловый reader

`install64typedimports` соединяет checked-IR потребителя с существующим
файловым `read64ownedimport`/`read64calllibrary`. Собственная ldt потребителя
сохраняется. Провайдер строится только из полностью проверенного файла
существующего scalar-library профиля; его C-тела, PC и карты конструктору
не передаются.

Это следующий участок после доверенного LOAD-сервиса. Допуск общих файлов
AWM здесь не добавлен: провайдеры ограничены прежним scalar-library профилем,
а потребитель пока создаётся доверенным checked-IR конструктором.

## Контракт installer

Владелец создаёт неопубликованный модуль с `Spec.load=read64ownedimport`,
затем вызывает `install64typedimports` до его публикации/исполнения.
`Native64TypedImportRequest` содержит прежние structural imports/strings,
массив classic-хешей из независимо скомпилированного `.m` и число записей.
Записи должны идти точно в порядке ldt потребителя. Хеши — проверка
согласованности native-метаданных, не аутентификация и не файловая authority.

До выделения памяти проверяются LP64/Word32, выбранный launch-профиль,
единственное владение неопубликованным модулем, callback, точное число
таблиц/имён/хешей, scalar-сигнатуры и геометрия импортных кадров. Кадры
должны иметь точный размер аргументов и нулевую root-карту. Имена сравниваются
как UTF-8 с Rune-пулом: Unicode поддержан, embedded NUL отвергается без
чтения за native-терминатором. Импортные Types — хвост массива Types
доверенного конструктора; это явная предпосылка private API.

После всех проверок одна allocation владеет копиями каждого structural
payload и пула. Исходные hashes нужны только во время проверки и не
сохраняются. Существующий installer без ldt использует тот же helper
копирования; его прежний контракт и empty-request поведение сохранены.
Ошибки и отказ allocation оставляют ldt, callback, REG и владение неизменными.
Default-профиль и отключённая сборка не разрешают установку.

Выполняемый `ILOAD` вызывает прежний reader: release/acquire, полный
ограниченный read, close, действующая admission-политика, полная проверка
провайдера и structural-сопоставление импортов. Каждый load читает и строит
новый экземпляр. Ни classic hash, ни старый cache не заменяют доказательство
полного файла. Имена, schema, opcode и файловые IDs не расширяются.

## Проверки

```sh
python3 utils/tests/native64-typed-files.py --limbo /path/to/limbo
ASAN_OPTIONS=detect_leaks=0 \
NATIVE64_CFLAGS='-O1 -g -DNDEBUG -fno-strict-aliasing -fsanitize=address,undefined -fno-sanitize-recover=all' \
  python3 utils/tests/native64-typed-files.py --limbo /path/to/limbo
```

Потребитель целиком компилируется из Limbo (`open`, `run`, `again`, `clear`).
`.m -H -R` даёт независимые structural-запросы; classic-декодер проверяет
порядок ldt/хеши и координаты кода. Провайдеры int, big и real компилируются
в обычные файлы `-64b`. У всех есть не запрошенный `init` с делением на ноль:
полная проверка включает это тело, но загрузка не вызывает его.

Стенд читает созданные файлы и подаёт их через контролируемые kopen/kread.
Reader, admission-порядок, file proof/constructor, linker, scheduler,
Limbo-инструкции и C/RX dispatch — настоящие реализации. Это не запуск
полного AWM и не замена namespace-примитивов полноценной ОС.

1152 C/JIT запуска варьируют оба режима, рост стека, кванты 1/3/1000,
знаки/размеры значений и восемь сценариев: успех, open failure, admission
refusal, short read, повреждённый файл, pin failure, dontcompile и close
failure. Каждый сценарий делает два LOAD, затем source-вызовы. Проверяются
точные результаты, MP-счётчики, защитные байты, отсутствие автоматического
init, баланс read/close/admission/constructor, pin transfer и полное
освобождение после ошибок.

Исходные request/name/hash-буферы портятся сразу после установки; исполнение
остаётся правильным. Для каждого scalar-варианта проходят 22 отказа до
выделения памяти, rollback единственной allocation, проверки Unicode/NUL и
cleanup. Default-режим не публикует installer и не делает I/O; disabled API
не читает даже заведомо невалидные входные адреса. Три активных контроля
обнаруживают удаление hash-проверки, root-проверки и копирования String-пула.
Их результат — семантический отказ до небезопасного teardown, не sanitizer.
Полный gate проходит ASan+UBSan/NDEBUG с detect_leaks=0.

Gate `files` добавлен двенадцатым в матрицу x64, ARM64, RV64 и Android
ARM64/Bionic и в полный port driver. Результаты новых целей подтверждаются
отдельно. Старая int/big namespace-цепочка, unused/wrong-kind refusals и её
активный copy-контроль проходят после выделения общего helper. Свежая полная
консоль и paired boot также проходят. 32-битный код сохранён.

Следующие ограничения: scalar-only файловые провайдеры, доверенный C-builder
потребителя, отсутствующий installer полного managed-графа AWM и
неподдержанные тела его стартовой цепочки. Общий `emuinit`/`sh`/AWM пока
не исполняется; запуск остаётся обычным Limbo `load`/`init`.


Предыдущий CI выявил устаревшее ожидание теста rollback: запрещённый LOAD
теперь отказывает до allocation. Тест сохраняет отдельную проверку раннего
отказа LOAD и проверяет защищённый rollback на некодируемом opcode 256;
проверки REG и освобождения владельцев не ослаблены.

Исправленные локальные регрессии проходят 960 module roots, 912 внешних
вызовов и 960 owned-import roots со всеми прежними активными контролями.
В предыдущем CI сам LOAD gate на 6528 запусков прошёл на всех четырёх целях;
остановка происходила в старом rollback-ожидании.
