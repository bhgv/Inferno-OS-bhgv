# Внешние вызовы из исходного Limbo на native64

[English version](dis64-typed-external-calls.md).

Раньше [проверка полного модуля](dis64-typed-modules.ru.md) вызывала поставщика
из клиента, написанного на C. Теперь исполняются целые функции Limbo-клиента:
компилятор переносит их внешние вызовы вместе с обычными инструкциями и переходами.
Поставщик по-прежнему создаётся конструктором полного нативного модуля.

## Пример

Обычный `provider.m`:

```limbo
Provider: module {
    identity: fn(value: string): string;
};
```

Клиент получает экземпляр модуля параметром:

```limbo
implement Client;
include "provider.m";
Client: module {
    keep: fn(p: Provider, value: string): string;
    forward: fn(p: Provider, value: string): string;
};
keep(p: Provider, value: string): string {
    first := p->identity(value);
    second := p->identity(nil);
    return first;
}
forward(p: Provider, value: string): string {
    first := p->identity(value);
    return p->identity(first);
}
```

`keep` сохраняет первый результат в локальной переменной, пока выполняется второй
вызов. `forward` передаёт последнему вызову место для результата своего вызывающего.
Библиотека не обязана иметь входную функцию. Автоматического вызова `init` нет.

```sh
LIMBO_DIS64_TYPED=1 LIMBO_DIS64_TYPED_EXTERNAL=1 \
    /path/to/limbo -i -I /path/to/interfaces -o Client.dis Client.b
```

`-i` отключает инлайнинг, чтобы вызовы оставались видимыми. Файл `Client.dis`
остаётся старым Dis и побайтно совпадает с компиляцией без диагностического флага.
Диагностика содержит доверенные таблицы компилятора, а не новый формат файла.

## Что переносится

У инструкции уже есть объявление вызываемой функции из `.m`. Номер импорта
берётся из `iface->offset`, существующая 32-битная сигнатура — из `sign(Decl*)`.
Имена методов ADT сохраняют квалификацию. Новых публичных сигнатур или ID нет.

Проверяется последовательность `MFRAME`, переносов аргументов, необязательной
привязки результата и соответствующего `MCALL`. На обоих концах должны совпадать
объявление импорта и переменная модуля. Переменная должна иметь тип модуля и
быть GC-корнем в FP или MP. Номер импорта ограничен диапазоном0..32767.
Сохраняются порядок, типы аргументов и выравнивание их нативных мест.

Поддерживаются простые аргументы byte/int/fix/big/real и ссылочные значения.
Копирование агрегатов, вариативные и полиморфные функции, обработчики исключений
пока отклоняются. Вычисляемый аргумент сначала нужно положить в обычную локальную
переменную. Переход разрешён на начало подготовки `MFRAME`, но не внутрь неё.
Только успешное завершение `MCALL` устанавливает унаследованный результат;
подготовка адреса результата и аргументов сама по себе этого не делает.

Закрытая схема `inferno-typed-external-v1` добавляет `externals`: границы вызова,
номер импорта, FP/MP и смещение модуля, имя/хэш, геометрию аргументов и контракт
результата. Старые схемы без нового флага не меняются. Для локальных и внешних
вызовов используется общий ограниченный анализ функций и потока управления.

## Исполнение и владение

В закрытый `Native64TypedCall` добавлены признак внешнего вызова и координаты
переменной модуля. Для локального вызова новые поля нулевые. Внешний вызов хранит
номер импорта и использует Type связанного экспорта для проверки размеров кадра;
нативный адрес внешнего кода в него не записывается. Цель выбирают существующие
`MFRAME`/`MCALL` через связанную таблицу экземпляра модуля.

Все проверки выполняются до записи выходного кода. При отказе каждый байт
выходного буфера остаётся прежним. Клиентский Module и внешний тестовый кадр
пока собирает доверенный C-код; тела функций целиком получены из Limbo.
Сопоставление имён/хэшей, клонирование MP, рост стека, возврат и очистка при ошибке
используют существующий runtime. Автоматической сборки импортов в Native64ModuleSpec,
регистрации в кэше или общего файлового загрузчика эта серия не добавляет.

## Проверки

```sh
python3 utils/tests/native64-typed-external.py --limbo /path/to/limbo
python3 utils/tests/dis64-typed-external-unit.py
```

Для ARM64/Linux QEMU используются прежние CC/NATIVE64_ARCH/NATIVE64_RUNNER.
Обе проверки включены в native64-port.py. Режим ASan для конструктора и подготовки
кода без исполнения стековых путей ошибок:

```sh
ASAN_OPTIONS=detect_leaks=0 \
NATIVE64_CFLAGS='-O1 -g -fno-strict-aliasing -fsanitize=address,undefined -fno-sanitize-recover=all' \
python3 utils/tests/native64-typed-external.py --limbo /path/to/limbo --materialize-only
```

Независимое чтение старого Dis проверяет17 функций/33 внешних вызова и хэши
сериализованных импортов. Отдельно проверены смешанные byte/int/big/string.
На x64 и ARM64/QEMU проходят по912 случаев:768 обычных,48 с повторным `MFRAME`
в цикле и96 с ошибкой после управляемого результата. Есть все четыре сочетания
C/RX клиента и поставщика, рост стека, кванты1/3/1000, граничные простые значения,
nil, локальные и унаследованные результаты, независимые MP и полная очистка.
Строки и списки здесь — непрозрачные графы с проверкой владения. Несколько
аргументов подтверждены анализом исходника, MP-модуль — подготовкой кода;
отдельных runtime-случаев для них эта матрица не содержит.

Восемь неверных входов проверяют атомарный отказ подготовки кода. Три активных
контроля отключают выравнивание модуля, границу импорта и изоляцию подготовки;
ещё один — проверку сигнатуры при связывании. Четыре контроля компилятора
отключают совпадение модуля, координаты аргумента, границу импорта и учёт
унаследованного результата. Принимается только точная семантическая ошибка,
а не падение или сообщение санитайзера. IR компилятора и конструктор/подготовка
кода проходят ASan/UBSan, исполнение — UBSan. Прежнее ограничение runtime-ASan
на размотке стека остаётся открытым.

## Что остаётся до Android GUI

Тестовая функция `loader` нужна для настоящих сериализованных хэшей импортов;
перенос её тела явно отклоняется. Исполнение `load` здесь не добавлено.
Оба файловых managed-профиля (`-64m`, `-64l`) по-прежнему отклоняют этого клиента.
Впереди общий writer/loader managed Dis64, допуск модулей в namespace/кэш,
оставшиеся операции с кучей и запуск Android GUI. Старые scalar/Sys/file-профили
сохраняют свои отдельные возможности и проверки.

Все16 исходников AWM/376 планов сохраняют старые байты; базовый анализ тел
остаётся14 принятых/346 отказов. Linux QEMU не подтверждает запуск на Bionic,
устройстве Android, работу AWM или готовый APK.

Продолжение: [сборка клиента с импортами](dis64-owned-imports.ru.md) убирает
ручную сборку клиентского Module из тестового C-кода.
