# Несколько типизированных вызовов в одном теле

[English version](dis64-typed-multiple-calls.md).

Продолжение [локальных результатов](dis64-typed-local-results.ru.md): теперь
переносятся вычисления до и между вызовами, несколько участков подготовки,
void-вызовы, унаследованный адрес результата и вызов внутри цикла.

```limbo
implement Calls;
Calls: module {
    count: fn(n:int):int;
    sum: fn(n:int):int;
    repeated: fn(n:int):int;
};
count(n:int):int {
    total:=0;
    while(n>0){total+=n;n--;}
    return total;
}
sum(n:int):int {
    x:=n+1;
    first:=count(x);
    second:=count(n);
    return first+second;
}
repeated(n:int):int {
    saved:=sum(n);
    total:=0;
    while(n>0){v:=count(n);total+=v;n--;}
    return saved+total;
}
```

Первый результат остаётся обычной типизированной переменной, пока выполняется
следующая функция. Цикл может повторить весь участок, начиная с FRAME.

```sh
python3 utils/tests/native64-typed-multi.py --limbo /path/to/host/limbo
python3 utils/tests/dis64-typed-multi-unit.py
```

Для ARM64/Linux QEMU задаются прежние CC/NATIVE64_ARCH/NATIVE64_RUNNER.
Оба набора включены в native64-port.py. Частный отчёт компилятора:

```sh
LIMBO_DIS64_TYPED=1 LIMBO_DIS64_TYPED_MULTI=1 \
    /path/to/host/limbo -i -o Calls.dis Calls.b
```

Ключ `-i` отключает встраивание исходных функций. Calls.dis остаётся классическим
байткодом; это ещё не сборка загружаемого управляемого Dis64 или APK.

## Проверки компилятора

Каждый участок содержит FRAME, аргументы в порядке объявления, необязательную
привязку результата и точный CALL. Сверяются начало функции, дескриптор, виды и
раскладки. Void-callee не получает привязку результата. Локальная ячейка имеет
вид результата callee; вид результата caller может отличаться, а преобразование
выполняется обычными типизированными командами после вызова.

Переходы остаются внутри функции и не входят внутрь подготовки. Вход в сам FRAME
разрешён: так работает цикл с вызовом. Вложенная подготовка аргументов пока
отклоняется. Если выражение аргумента компилятор пишет прямо через подготовленный
указатель, вычислите его заранее в локальную переменную. Aggregate-копии,
varargs/generics, обработчики исключений и модульный MCALL пока закрыты.

Контекст одного корня индексирует инструкции и функции, строит каждый план
потомка один раз и использует его для повторных вызовов. Активный цикл отклоняется;
высота сохранённого графа учитывается при проверке всей глубины. Ограничения:
4096 функций,65536 инструкций,64 функции в цепочке и32 MiB суммарной геометрии
кадров/MP и листьев раскладки. Кэш освобождается и после успеха, и после отказа;
наружу передаётся только собственный план корня. Исходный IR и байткод не меняются.

Успешный inherited-CALL определяет результат caller при условии нормального
возврата: для этого служит частный маркер32. Запись аргументов64 и привязка
локального адреса128|контракт этого не доказывают. Каждый достижимый RET требует
настоящего определения результата на каждом входящем пути.

## Частный отчёт и нативные инструкции

Схема принятого caller — inferno-typed-multi-v1. Каждая запись calls содержит
[PC_FRAME,PC_CALL,старый_PC_callee,старый_ID_дескриптора,смещение_результата,
размер_OR_бит_ссылки,inherited]. PC относительны телу, кроме входа callee;
смещение равно32 для inherited и0 для void, контракт void равен0.
Шестипольные команды и v2-листья сохраняются.

Доверенный сборщик сопоставляет Type, вход и нативный ordinal каждого callee.
native64typedmulticode проверяет неперекрывающиеся упорядоченные участки,
физические границы аргументов, адреса результатов и переходы до изменения выхода.
Вход и выход должны быть раздельны; смысл полей, видов и целей по-прежнему
обеспечивают компилятор и сборщик. Это не проверка произвольного чужого образа.

Прежний доверенный cstep связывает новые адреса до decode/JIT, проверяя размер,
карту GC и живую геометрию стека. Унаследованный адрес передаётся всеми8 байтами
через FP32. Подготовленный указатель в служебном поле40 переиспользуется между
завершёнными участками. При материализации нет аллокаций/callbacks. Module/Frame,
обычный LEA и публичные ID Dis64/ISA не меняются. Сама привязка остаётся на C
в режимах C/RX; аппаратный LEA и конкурентный pin/ABA не добавлены.

Тест собирает частный нативный Module из отчёта. Общая карта MP через heapz
инициализирует nil-корень; Word-поле out позволяет проверить void-вызовы.
Это доверенная инициализация теста, не общий writer/loader. Внешний вход и его
начальная привязка результата пока задаются на C.

## Результаты

На каждой x64 и ARM64/Linux QEMU проходят480 запусков:384 исходных и96 частных
ошибок после последнего управляемого вызова.23 функции содержат32 участка.
Покрыты шесть видов результата, void/inherited, сохранность первого значения,
второй nil-результат, вычисления до вызова, вложенность, циклы, рост и кванты.
При ошибке внешний результат сохраняется, а все локальные владельцы очищаются.

1728 повреждённых привязок на архитектуру сохраняют адрес/результат/PC без
аллокаций.12 структурных отказов сохраняют выход. Проверены4 условия компилятора,
2 условия нативного адаптера,2 прежних условия привязки и4 повреждённых отчёта:
нужен точный смысловой отказ, crash/timeout/sanitizer failure не засчитываются.
Отдельно проверены разные виды результатов, общий граф из40 функций, граница64
и отказ для взаимной рекурсии. Host compiler/core проходят ASan/UBSan,
ARM64 core/runtime — UBSan. Ограничение runtime-ASan unwind остаётся открытым.

String/list identity здесь передают непрозрачные владеющие графы; настоящие
операции строк/списков/Unicode/GC имеют отдельные прежние проверки. Конкурентный
GC и планировщик ОС в ограниченном тесте не запускаются.

Обычный AWM остаётся14/346, одинаковый `-i` —17/380. Байты16 исходников,
376 раскладок и191 прежнего образа сохранены. Оба файловых профиля пока отказывают
этому управляемому модулю. Общий writer/loader, MCALL/heap-операции и старт GUI
ещё впереди; запуск Android/Bionic, AWM и готовый APK не заявляются.
